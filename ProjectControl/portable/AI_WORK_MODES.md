# Project Control｜AI 岗位、方法、知识与执行分离

Role 是经负责人委任的工作职责。Method/Skill 是某类研究、设计、实施或审查的方法。Context 是目标项目的历史、事实、需求与决策证据。Authority 是外部人类批准及工具权限。这四者绝不可互相替代。

## 事实发现、有效性判断与补全职责

方法不只是告诉 AI 去搜资料。必须区分已找到来源、资料主张是否真实、是否仍然适用、是否经过正式决定，以及什么工程依据确实缺失。调查须考虑旧批准与后来更改；单次 GitHub 关键词查询无结果不构成缺失证明。协调者发现必要的缺失资料后，应组织对应研究、需求或设计候选和审查，而不默认要求负责人补文件。证据与补全指南见 EVIDENCE_AND_REMEDIATION.md。

## AI 入场
先确认目标项目、当前任务和岗位；再按任务载入对应工作方法、查找项目上下文，形成有限范围的判断，并报告未查明事项。不能因为谁先读取 START_HERE 就自封项目经理；负责人已经明确角色时不得再次询问。发现信息不足时继续调查，而非自动启动下一阶段。

## 方法选择
存量接管与跨对话恢复先用 CONTEXT_DISCOVERY.md；专题研究、需求、架构、设计、实施、集成和验证使用 process_catalog.json 的相应工作方法。并行工程活动可以并行；方法不是强制瀑布，也不自动产生 Gate。当前执行任务仍须按 TASK_CONTRACT.md 取得精确设计、范围和独立授权。

## 客户端限制
GitHub 中的指令文件不会自动注册为 ChatGPT 网页端系统指令或原生 Skill。可以将通用方法封装为受支持客户端的 Skill/Agent 适配形式，但必须确认真实可用性；不可凭文件名推断已加载。

## 真正的强制点
AI 指引不能代替程序检查。代码修改、合并、文件清理、发布与硬件操作仍由真实任务合同、GitHub/操作系统权限及外部授权控制。报告和发现审计本身不给 READY、PASS 或 ACCEPTED。

## 证据评价的执行落点（4.5）

管理 AI 根据项目事实准备 `project-control-context-assessment/2` 记录，将其作为**候选**通过合法的受控操作交给当前目标项目；必要的补全工作应关联现有项目交付和 WBS 候选工作，不能只在聊天里说“建议完善”。当前 `context_workflow.py` 可受控存储和建立候选关联，不会自动批准或向 Codex 发布任务。未能访问本地服务时只能形成远端待审材料并说明未同步，不能谎称已写入。
