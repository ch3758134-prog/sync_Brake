# Project Control｜工程成果交付、负责人审阅与正式批准协议

状态：**4.6 工程候选**，不是项目正式治理政策或已获批准的发布版。
适用：研究报告、需求、设计、项目计划、测试/验证、管理审查意见、软件发布候选。
目的：防止 AI “自己研究—自己宣布完成—直接写 GitHub—又说已交付”，而负责人根本没有阅读成果、判断差异或作出决定。

## 1. 不同动作的真实语义

| 动作 | 谁有职责 | 能做什么 | 不能代表什么 |
| --- | --- | --- | --- |
| 工作与事实调查 | AI 在已知岗位/范围内 | 检索、核对、分析、保存临时草稿、向负责人汇报事实 | 正式基线、审批、授权 |
| 保存内部草稿 | 研究/执行 AI | 保存完整正文、证据与修改差异；仅本机候选 | 已向负责人展示、已获批准 |
| 准备负责人审阅 | 管理 AI | 将完整候选放进负责人待审队列，并在 ChatGPT 中说明项目问题与结果 | 用户读过、用户同意 GitHub 发布 |
| 负责人审阅 | 实际负责人 | 阅读全文、与上一有效版的差异、限制、拟发布范围；退回/暂缓/允许候审公开 | 内容正式批准、产品验收、自动执行 |
| 允许发布候审 | 负责人针对**同一候选版本**作出的流转决定 | 特定目标发布该版本为 Draft/候选以便进一步审查 | 批准需求、计划、Gate、代码或实物操作 |
| 正式工程批准 | 可信的正式批准渠道 | 针对确定对象、版本、范围及条件生效，能追溯外部人类身份 | 自动推广到新版本或下一阶段 |
| 执行许可与实际验证 | 单独受控机制/测试人员 | 对具体可执行任务/设备动作/验收按要求逐项授权和取证 | 研究完成就是实施 PASS |

**“继续”“改吧”“提交吧”“我看可以”均须结合具体对话及对象解释。** 用户明确要求修改某个代码候选，许可范围仅是该候选的实际开发工作；不能从中推导正式发布、合并、P0/G1 批准或刷写权限。不要强迫用户每次读写内部草稿都审批，但当需要让 GitHub 上的正式管理/交付记录发生副作用时，必须有明确内容与允许操作范围。

## 2. 向负责人出示的内容

AI 应先在 ChatGPT 自然语言中交代：
- 当前项目问题、为什么现在需要成果、与现行项目目标的关系；
- **完整的可审阅正文**或清晰可展开的全量内容（不能只给摘要/链接/内部 JSON）；
- 与上一个有效成果的差异、来源、新增结论、未查明项、风险和对上下游的影响；
- 专业技术审查是否完成；哪些问题尚不适合让负责人自己技术判断；
- 此时具体需要的决定（审阅候选、退回修订、允许候审公开、正式内容批准或实施授权），及许可之后**准确会发生什么**。

没有要求作决定的进度报告，可以正常向负责人汇报，不制造审阅门槛；但**不能把普通报告写到 GitHub 后再倒称已交付**。

## 3. 本地候审数据与两个独立接口

候审稿的完整正文首先保存在目标项目本地 Git 管理元数据目录下的 `project-control/deliveries.json`（通过 `git rev-parse --git-path` 定位，支持 linked worktree）。它**不是** `.project-control/management.json`，因此不会被该 JSON 的远端同步器意外发布。每个版本有 SHA-256、历史、状态、拟发布目标和来源。

- 具有本地日常管理令牌的客户端可以在 `POST /api/delivery-draft-action` 使用 `stage_delivery / revise_delivery / offer_delivery_review`，只能创建和提交**待审候选**。同一令牌不能通过普通 `/api/action` 授予候审发布许可。
- 负责人审阅界面通过 `GET /api/delivery-reviews` 读取完整候选；管理或独立审阅令牌才能读取。负责人工作台还允许通过“导入／修订 AI 候选成果”将 AI 准备好的完整 JSON 候审包预览后保存，不要求负责人自己撰写研究；所有入库均为私有内部草稿，改动旧正文会失效既有候审发布许可。普通 `/api/model` 不含敏感全文，仅显示数量。
- `POST /api/owner-delivery-decision` 需要**独立审阅令牌**、精确版本/正文 SHA、明确勾选与非空审查理由；仅接受 `REQUEST_CHANGES / HOLD / ACKNOWLEDGE_INTERNAL_REVIEW / ALLOW_CANDIDATE_PUBLICATION`。其中 `ACKNOWLEDGE_INTERNAL_REVIEW` 仅记录已阅读，不允许对外发布，也不是正式工程批准；标为 `NO_EXTERNAL_PUBLICATION` 的成果不可以获得对外候审发布许可。旧版本许可不会继承到修改后的新正文。
- 上述接口对项目身份、状态和存储修订执行 CAS；只有本地受控写入，**不会自动 Git commit、push、发 Issue 评论或创建 PR**。实际 GitHub 发布必须通过单独控制的发布动作，再核验对象、发布许可、目标和真实远端结果。
- 若新 AI 只有 GitHub 网页连接而无法访问用户的本地审阅存储，必须**先在聊天中展示成果并请求明确的发布许可**；不能假装本地审阅状态已经写入。受支持的托管工作平台需另外实现可信的 review+publication handoff。
- 本地令牌不是密码学意义的“这个真人确实阅读过”，仅证明客户端持有该进程的独立能力令牌。正式产品/范围/需求/设计批准必须从可信人类外部渠道独立核对。

旧 `process_control.review_requests` 是内部候选工作流的**准备记录**：从 4.6 起状态 `PREPARED_NOT_PRESENTED`，不是用户已收到审核；历史 `REQUESTED_NOT_APPROVED` 仅作历史记录读取，不自动补出全量成果或负责人已读事件。旧 `record_ai_work_report` 只保存内部报告，不能代替完整候审交付。

## 4. 交付前明确核查五个条件

1. **谁的项目？** 目标仓库/项目身份准确；管理工具源码与业务项目区分。
2. **交付的是什么？** 具体成果、版本摘要、完整正文或代码 diff、针对的用户任务和审查范围。
3. **负责人知道并参与了吗？** 是否已在可阅读界面展示，后续真正需要什么决定？未确认时状态不得升级。
4. **发布到哪里？** Draft PR、候审文档、Issue 候选评论或正式基线，目标与影响不同，用户授权不可跨用。
5. **后续能做什么？** 候审公开不等于正式批准、合并、设备动作或 Codex READY。

对所有正式成果应用合理范围裁剪；普通工作记录/调查附录无需强迫用户逐篇签核，但必须保证不会因此擅自改变正式工程状态或对外公开未经允许的完整候审文档。

## 5. 必须防住的反例

- AI 以“继续”为由创建 GitHub Issue 长评论，自称交付完成：**禁止**。先展示可审稿，明确发布对象与许可。
- 完整报告只留下 GitHub URL，负责人没读正文：**未完成负责人审阅**。
- 用户允许将 G1 r4 发为 Draft，不代表 G1 正式 APPROVED。
- AI 修改批准过的文档内容，用旧许可再发布：**摘要/版本不匹配拒绝**。
- 普通管理 Token 自称 Owner：**专用审阅操作拒绝**；持有 Review Token 仍不代表已验证正式批准身份。
- 内部草稿存入 Git 跟踪的管理账本并被普通 sync 推走：**不得采用**，使用 Git 元数据隔离。
- 只提交一个技术审核 `ADEQUATE_CANDIDATE` 而无可读成果：**不得称负责人已审**。
- 发布候选之后直接将计划/任务标为 READY 或验收 PASS：**权限不成立**。
- 因一项上游变更而自动撤销全部无关成果：**应按依赖精确审查**。
- 现有 GitHub 连接仍具有直写 main 的宽权限：该能力可以绕过本地程序，**不能宣称本机制 ENFORCED**，需以 GitHub Rulesets/受限令牌/发布代理做真实外部控制。

## 6. 外部设计依据（借鉴，不宣称标准认证）

- [OpenAI Agents SDK—Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)：副作用前暂停、记录精确动作参数、获授权后恢复；审批状态需由可信服务保存，不能只用 AI 生成内容。
- [OpenAI Agents SDK—Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)：人类审批必须有服务端保存的待审操作、独立授权与重放保护。
- [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)：PR 审查与代码合并分开，可要求变更后失效旧评审。
- 既有 Project Control `REPORTING_PROTOCOL`、`PROCESS_SYSTEM`、`TASK_CONTRACT`：过程责任、技术质量审查、正式决策和执行许可须分离。

## 7. 当前未实施的能力

未实现：从本地候审状态到 GitHub Issue/PR 的完整原子发布、GitHub 账号级人类身份核验、跨机器/ChatGPT 对话共享私有待审全文、正式工程批准/发布的端到端可信审查服务。这些不可由写一个 `ALLOW_CANDIDATE_PUBLICATION` 字符串冒充。

下一步真实验收：两个独立令牌与 HTTP 反例测试、Windows 本地完整正文审阅、旧版兼容、候审许可后受控发布器、正式外部批准与内容版本绑定，逐项保存原始证据。
