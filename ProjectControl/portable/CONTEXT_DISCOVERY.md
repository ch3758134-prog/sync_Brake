# Project Control｜项目上下文发现与 AI 接管方法

本文件是候选工作方法，不赋予正式批准、编码或 GitHub 权限。项目认识不能从代码目录、README 或最新 commit 直接推导。

## 调查顺序
1. 确认目标仓库与管理工具仓库的区别、用户指定的 AI 岗位、真实来源和当前任务。用户已指定岗位时不得重复询问。
2. 建立资料搜索地图：项目目的和产品对象、使用者及实际场景、范围和约束、需求及其变化、研究与实验、架构和设计理由、历史决策及撤回、验证事实、当前计划和风险。根据工作性质裁剪，并说明为什么不调查某类资料。
3. 广度优先：先找根入口、历史资料索引、主要文档、相关 Issue/PR、版本与关键决策。再沿两条链深挖：目的→需求→设计理由→实施/验证，以及问题→争议→修改→现行决定。不得只查看最新主线代码。
4. 给关键主张保留证据定位、时间/版本、适用范围和证据状态。OBSERVED 是直接核对；REPORTED 是历史或用户陈述；INFERRED 是推断；APPROVED 须有正式授权来源；UNKNOWN 和 CONFLICT 不能掩盖。
5. 源头冲突时优先追查决策为何变化。新提交不能自动覆盖产品目标，老 Gate 不能自动否认后来明确撤回的方案。缺信息时继续检索或报告具体缺口。
6. 是否可以推进由当前任务需要哪些已证实的前提决定，不由搜索次数、文件数量或填表数量决定。可以局部充分，不得自称整个项目已被完全了解。缺少关键前提不能生成正式实施任务或批准。
7. 对负责人先讲项目是什么、为什么做、主要问题、判断、下一步和真正需要的决定；附上简短的检索覆盖、冲突、未知和来源记录。不要让 HEAD/P0/表格成为主要报告。

## 按岗位确定搜索广度
协调 AI 优先恢复项目目的、用户、范围、历史决定、研发背景和近期矛盾；专业研发 AI 深入核对任务对应的需求、技术依据、接口与影响；集成/审查 AI 聚焦准确版本、跨模块合同和真实证据；Codex 只依据当前授权的具体任务合同执行，不把全局探索当作编码授权。

## 工作记录与当前资料有效性

检索层与评估层分开：

- `context_discovery.py` 的 `project-control-context-discovery/1` 为历史记录格式，旧 `COVERED` 只表明有来源，**不得解释为当前适用或形成实施依据**。
- 新的 `context_assessment.py` 使用 `project-control-context-assessment/2`，将检索尝试（包括空结果和工具失败）、来源、关键主张的当前适用性、缺失资料调查及补全行动分开记录。详细方法见 [EVIDENCE_AND_REMEDIATION.md](EVIDENCE_AND_REMEDIATION.md)。
- 能找到来源不代表经过审查；有历史批准不代表当前仍适用；资料缺失需要协调者组织补全，不能只是记录 UNKNOWN 后把工作停掉。
- 结构检查不能证明 AI 真正理解项目，也不授予批准。旧记录只读，经过重新调查另建新版，不能静默升级。

未覆盖资料和失败的检索渠道不得隐藏，用户不需要手工整理已有 GitHub SHA、PR 或历史资料。

## 跨对话与客户端
GitHub 中一个 SKILL.md/AGENTS.md 并不会让所有 ChatGPT 网页对话自动执行它。新对话须被明确引导读取入口，记录实际获得与尚未取得的来源。面向不同客户端可配适配器，所有项目事实与正式决策仍以目标项目的可追溯资料为准。
