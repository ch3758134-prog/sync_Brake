# Project Control｜证据有效性、资料缺口与工程补全方法（通用候选）

## 任务和出发点
AI 不仅要“找到文件”，还要判断它是否可以支撑**当前**的工程工作，并在存在缺口时组织合理的补全。不要将这项工作固定为一个所有项目都必须完整完成的 Gate。按具体任务的风险、变更范围和资料成熟度裁剪。

**三种不可混淆的事情**：
1. 找到了某份资料（source discovered）
2. 资料主张经过评估，形成当前适用的**候选**判断（claim assessed）
3. 判断获得有权者正式批准并且对应实施有独立授权（approved / authorized）

以上三者不能由同一个 `COVERED` 字段代表。

## A. 先调查“找不到”的原因
一个 GitHub 内容关键词搜索没有结果，**既不能证明资料缺失，也不能证明项目不完整**。它可能来自分词、索引范围、旧分支、离线文档、历史记录、命名习惯或权限。

AI 应优先检查适当的替代路径：目录/树遍历、历史版本、来源索引、Issue/PR、附带资产、用户先前确认的资料或必要的外部资料。记录每种查找方法、查询/路径、结果与限制。如果工具返回错误或拒绝访问，记录 `SEARCH_INCOMPLETE`，不冒充“未找到”。

对于确实缺少的**适用**工程资料，应解释为何目前需要它、已经调查过哪些来源、可以使用什么材料补写、是否存在更合适的现有工作产品，然后提出补全方案。资料的必要性由工作任务决定，不能硬编码“每个项目必须都有同名产品定义文档”。

## B. 对找到的资料做实质审查
每条关键主张应根据实际情况追问：
- **出处**：谁提出、什么时候、版本/提交、原始观察还是转述、能否取得原件？
- **形成理由**：支持该说法的使用事实、研究、试验、设计论证是什么？
- **历史变化**：后续有无正式批准、反对意见、变更、撤回、替代或过期条件？
- **现实适用性**：该主张适用于哪个产品/版本/设备/用户场景？相关条件是否仍成立？
- **证据边界**：文件确认不等于运行通过；测试声明不等于真实测量；批准一份旧设计不等于今天仍然适用。

建议使用 `UNASSESSED / SUPPORTED_CANDIDATE / HISTORICAL_ONLY / SUPERSEDED / CONFLICT / UNKNOWN` 评价主张，而非统一标“已核实”。`SUPPORTED_CANDIDATE` 的意思只是**经本轮调查的当前候选依据**，不是正式批准。

## C. 缺口的负责人、工程措施与追踪
确认缺口后，项目协调 AI **负责组织后续行动**，不把找资料的责任直接交还用户，也不默认亲自完成全部专业研究。典型行动：
- `RESEARCH_SOURCE`：继续查证资料和历史来源
- `REVIEW_EXISTING_ARTIFACT`：审查现有工作产品有效性
- `RECONCILE_HISTORY`：恢复变更/批准/撤回链路并提出冲突解决
- `DRAFT_MISSING_ARTIFACT`：形成缺失项目定义、需求或设计的**候选成果**
- `VERIFY_REALITY`：安排必要的试验或实际使用调查
- `OWNER_DECISION`：仅在需要负责人真实取舍或批准时请求决定

行动应明确理由、预期成果、适用专业、必要输入和下游用途；由项目现行过程与任务准入规则决定谁执行、如何审查、能否发布实施任务。调查报告里只能写 `PROPOSED_NOT_AUTHORIZED`，不可直接发放 Codex 权限。

## D. 防止程序“检查字段即批准”
`context_assessment.py` 校验新发现记录的来源链接、搜索手段、证据审查结构、缺口补全动作和局部工作前提。它不能判定资料内容是否真实，也不能证明已经检索完所有可能来源。

`ASSESSED` 仅表示至少有可解释的当前候选论证，**仍需专业审查**。`GAP_CONFIRMED` 仅表示按记录的调查范围“确认缺口候选”，不是全球不存在该资料的证明。两个独立搜索手段是最低的结构性防止单次空搜索误判，而非充分性的科学标准。

旧 `project-control-context-discovery/1` 格式和 `COVERED` 只允许历史阅读，不能自动迁移、继承当前有效性或直接编成正式任务。需要重新审查后按新格式形成独立记录，不静默改写旧资料。

## E. 项目管理负责人与 AI 的职责
项目负责人参与影响目标、范围、成本、风险、对外承诺、重要技术取舍和正式批准的决定；**不应被要求代替 AI 完成日常 GitHub 搜索**。协调 AI 主动判断信息断点并协调对应专业；专业 AI 形成研究或设计候选；审查岗位寻找反证和影响；本地 Codex 仅执行已获授权的具体任务。

对负责人优先说：现在的项目问题、为何重要、已经能认定什么、哪项仍不能认定、将如何补齐、需要哪项真实决定。复杂来源和版本可以作为证据附录。

## F. 最小可执行使用方式

1. 使用 `context_assessment_example.json` 了解 v2 字段，按照实际目标项目创建独立调查记录。示例是虚构的，不得复制为真实项目证据。
2. 每个主题可标 `NOT_SEARCHED`、`SEARCH_INCOMPLETE`、`SOURCES_FOUND`、`ASSESSED`、`GAP_CONFIRMED` 或 `NOT_APPLICABLE`。一个主题的 `SOURCES_FOUND` 不能视为工程依据已成立；`ASSESSED` 仍仅是当前候选专业判断。
3. `claims` 中 `SUPPORTED_CANDIDATE` 须有来源、论证、历史变更检查和当前适用性理由。无法查证时写 `UNKNOWN` 或 `CONFLICT`，不补造理由。
4. 缺口候选至少记录两种独立发现方法、没有把工具错误当资料不存在，并给出状态为 `PROPOSED_NOT_AUTHORIZED` 的补全行动。这个最低结构检查不替代专业充分性审查。
5. 在管理系统包根目录运行 `python portable/context_assessment.py portable/context_assessment_example.json` 测试通用样例；真实项目记录可保存到目标 `.project-control/context_assessment.json`。**CLI 不写入文件、不批准、不给任务 READY**。
6. 负责人本地 Web 工作台的“资产与正式依据”页只读展示该记录；不需要为了测试用户自行填写管理表格，AI 应当负责建立候选、说明来源并安排适用审查。

当前未提供跨 GitHub 和本地 Web 的自动证据同步事务，不假称编辑一次报告就已回写远端。


## G. 工程补全与现有工作台的正式关联（4.5 候选）

新评价的受控写入通过 `context_workflow.py` 的 `record_context_assessment`：将现行 /2 调查记录追加到目标项目 `management.json.context_reviews`，保留摘要与历史版本；不覆盖旧案、不改变批准。当前调查里的补全行动可用 `propose_context_remediation_work` 创建并关联 `management.work` 中一个未授权的候选工作，前提是已建立合适的候选交付、当前调查版本一致、专业类型相容且未重复关联。新证据版本会标记已有引用工作需要复审。

两项动作都使用 Web 工作台的本地令牌和 `expected_revision` CAS；GitHub 远端状态和正式人类授权依旧独立。一个新的管理候选不构成需求批准、代码执行许可或产品验收。旧 `context_assessment.json` 可读但不自动迁移为新的台账数据；本地管理数据不自动推送。
