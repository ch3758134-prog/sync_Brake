# BrakeSync｜汽车电子软件工程与 C 编码强制规范 V1.0

> 文件编号：BS-SW-STD-001  
> 日期：2026-11-14  
> 状态：`PROPOSED_FOR_PROJECT_ADOPTION`（负责人提出“全面严格参照车规级”，本文件给出可执行制度；不是合规认证证书）  
> 适用对象：BrakeSync 三版共用固件核心、BSW/外设驱动、设备协议、启动与升级、安全关键应用、测试代码及构建系统；第三方 SDK 按供应商软件专项控制。  
> 当前基线：`BS-P0P8-BASELINE-003 / V0.3`，产品顺序为 V1 真实功能测试 → V2 LCD 正式交付 → V3 App；目前 PCB 未完成，以全新源码和真实云途开发板开展受控开发。

## 0. 执行原则（强制）

1. **不再使用“个人项目简化版”“演示够用”“能编译就行”作为设计准则。** 从第一行新代码起就要求需求、软件架构、接口契约、静态分析、单元/模块/目标测试、版本追踪和变更控制。开发任务可以分批实施，但质量门禁不能以后再补。
2. 项目以**车载安全相关控制器**的工程严谨度为目标，并非已经通过车规/ASIL/ASPICE 认证。严禁未经危害分析、目标市场确定和实测，声称任何 ASIL、ISO 26262、MISRA 或产品级合规通过。
3. **禁止以流程文档代替设计和真实测试**。每个质量门禁必须有原始工具输出、适用范围、版本、责任人和审核记录。工具未安装或不具许可时记为 `BLOCKED`，不得写 `PASS`。
4. 遵循 ASW/BSW 分层思想，应用逻辑不得依赖芯片寄存器与 SDK。**不因严格质量目标就凭空引入 AUTOSAR Classic 平台、RTE、OS 或不必要多层 HAL**；是否引入均需资源、时序和需求证据。严格是规范和可验证性，不是堆砌框架。
5. 当前实板只允许**无实际房车制动功率**的开发和验证。真实功率执行必须先完成目标制动器/电源/功率电路、安全许可与专用台架评审。

## 1. 标准和版本基线

| 类别 | 本项目采用的对标依据 | 用途与实施界限 |
|---|---|---|
| C 语言 | ISO/IEC 9899:2011（C11）及经批准的受限语言子集 | 固件 C11、编译器诊断和可移植行为；不假设 MCU 工具链完整支持全部 C11 库 |
| C 安全编码 | **MISRA C:2025**（当前版） + 官方 MISRA Compliance 指导与勘误 | 强制建立逐条适用性、工具覆盖、违规与偏离审批；取得合法标准和合格检查工具前不宣称 MISRA 合规 |
| 软件功能安全 | **ISO 26262:2018**，侧重 Part 3、4、6、8、9 | Item Definition、HARA、安全目标、系统/软件安全需求、架构、测试和配置管理。标准适用性/ASIL 须按产品和法规独立判断 |
| 研发过程 | **Automotive SPICE 4.1（2026-08）** | 需求、系统/软件架构、详细设计、单元验证、集成验证、质量保证、问题/变更/配置/验证管理等过程评审参考。能力等级需独立评估，不自称达到等级 |
| 网络安全 | **ISO/SAE 21434:2021** | 特别关注未来蓝牙/App、诊断与软件更新的 TARA、身份权限、数据完整性、配置防误用；不以加密口号替代实际设计 |
| 更新工程 | **ISO 24089:2023** | 若后续支持固件升级/OTA，适用升级适配、完整性、回退和安全更新流程；未决定 OTA 不代表不规划升级风险 |
| 供应商 SDK、MCU、接口 | 经核对的云途 MCU 数据手册、Errata、YCT/SDK、评估板原理图、真实模块规格书 | 真正的寄存器、ISR、DMA、引脚、时钟和信号依据；不根据其他 MCU 家族推断 |

> 说明：MISRA C 文本具有许可限制；项目应自行取得合法授权版本。此规范制定的是项目**落实措施**，不复制 MISRA 全部规则正文。所有正式检测工具的 MISRA:2025 覆盖情况及局限必须记录。

## 2. 适用范围和代码等级

所有新代码都须经历相同的受控流程，安全相关模块增加更严格的证明和独立检查，而不是让其他模块失去管理。

| 代码类别 | 典型范围 | 强制控制 |
|---|---|---|
| 安全相关业务 | 制动意图、运动质量、制动控制、状态、故障、执行许可、关键参数 | 最严格的需求追踪、独立评审、MISRA、静态分析、边界与故障注入、时序/资源证据 |
| 基础与驱动 | 启动、时钟、GPIO、Timer、CAN、UART DMA、NVM、Watchdog、PWM/ADC | 硬件来源、复位状态、IRQ/DMA 竞态、错误/超时、资源约束、目标实测、MISRA / 供应商例外记录 |
| 非实时管理 | LCD、BLE、维护诊断和配置界面 | MISRA、健壮协议/权限、错误回执、用户状态新鲜度、与实时控制隔离 |
| 第三方及生成物 | SDK、启动/链接脚本、YCT 生成代码及外部协议库 | 固定版本/哈希、来源/许可证、已知缺陷、适用性评估、修改限制、工具链/集成验证与例外文件 |
| Host 测试/仿真 | 单元测试、Fake/Stub、测试输入/工具 | 需求与测试结果可追踪；模拟代码必须与 Target 实现隔离，生产构建不可链接测试替身 |

## 3. 语言规则与接口约束（项目补充强制规则）

1. **禁止运行期动态堆分配**（`malloc`/`calloc`/`realloc`/`free`）、变长数组、递归、未经界定的函数指针调用链、无界循环和不受控栈占用。确需偏离必须提出书面风险评估、上下限证明和授权，不得口头豁免。
2. 使用 `stdint.h` 明确宽度的整数类型表达跨接口量化数据；物理信号注明单位、坐标、比例、有效范围、时效与无效值。禁止隐式单位转换与用魔法常量表示物理量。
3. 严格控制隐式类型提升/有符号与无符号混合、溢出、移位、整数截断、枚举类型错误映射、别名违规、非对齐访问、未初始化内存与越界。
4. 每个公开 API 明确输入合法范围、`NULL` 处理、超时、返回状态、错误码、调用上下文（任务/ISR）、重入性、所有权、线程安全及初始化依赖。原则上业务 API 必须有可观察错误结果；`void` 仅用于明确无失败路径的动作。
5. 每个模块只拥有自己管理的状态。默认静态分配且资源上界已知，禁止不可追踪的可写全局变量。跨模块共享通过受控接口、只读快照或明确定义的通信方式。
6. 所有函数都必须覆盖初始化前、重复初始化、运行中、非法参数、资源忙、超时、中断/重启及错误恢复路径。错误不能仅通过忽略返回值“处理”。
7. `assert` 只能作开发期不变量检查，不能作为产品功能的唯一错误处理或物理输出禁止手段；编译时被禁用也不能改变关键运行逻辑。
8. 安全相关数据的来源、新鲜度、版本、有效性必须随数据传递；丢帧、失时、冲突、数值越界不能默认为正常值。
9. 严禁业务层直接更改 MCU GPIO/PWM/CAN/UART 寄存器，严禁设备协议解析混入通用中断处理器；`main()` 只负责系统启动、调度入口和明确的故障路径。
10. 不允许随意使用 `#pragma`、内联汇编、编译器专有属性、裸指针类型重解释、直接宏封装复杂逻辑；硬件/工具链需要时应集中封装且建立批准的偏离条目。
11. 对数组长度、DMA 缓冲、帧解析、配置数据及版本字段进行上界检查；所有未可信输入先校验再使用。字节序与线协议必须有明确编码/解码，不直接把 C 结构体内存当线协议发出。
12. 指针、const、volatile 和原子/中断同步必须正确：**`volatile` 不是原子操作，也不能解决竞态**。ISR/DMA 与主循环共享数据应定义同步协议和缓存一致性策略。
13. 中断处理器必须有可分析最坏执行时间，不做动态分配、阻塞等待、复杂业务或无界重试；中断源清除顺序必须来自对应 MCU/SDK 文档。
14. 看门狗由经过审查的系统监督逻辑按运行健康条件驱动；禁止“任意定时中断无条件喂狗”掩盖软件死锁。
15. 关键配置必须区分接受/生效/可靠保存/读回；数据结构带版本兼容与完整性处理。CRC 只能检测偶发错误，不代替安全权限或强认证。
16. 功率输出必须在**独立审查的实际硬件安全设计**下受控，不能以布尔变量、PWM=0 或软件复位来宣称物理断电能力；在当前开发板无真实功率输出 API。
17. 命名采用稳定英文、统一模块前缀；关键中文注释解释契约、硬件出处和安全理由，不用注释代替代码清晰度；所有文档仅 Markdown。

## 4. 统一源码与目录契约

```text
firmware/
  cmake/                 # 受控构建脚本、编译器/编译选项
  config/                # Variant/Board/Release 配置（相互独立）
  include/brakesync/     # 对外公开、稳定 API
  src/asw/               # 输入质量、运动解释、控制、状态、配置、诊断
  src/bsw/board/         # 实板引脚/时钟/SDK 版本与启动适配
  src/bsw/drivers/       # MCU GPIO/UART DMA/CAN/Timer/ADC/PWM/Flash 等驱动
  src/bsw/devices/       # CAN IMU、BLE、LCD 等设备协议
  src/bsw/services/      # 时间、NVM、事件、故障记录/健康监测
  target/ytm32b1le0/     # YCT 官方生成的独立目标工程及受控集成
  tests/host/            # 可运行的主机单元测试、异常/边界用例
  tests/target/          # 实板驱动与时序/故障注入测试，不接功率链
  qa/                    # 静态分析配置、MISRA 偏离、审核记录、工具日志
  docs/                  # 需求追踪、模块说明、验证计划、已知风险
```

新增一个模块时至少要创建：公开接口/私有实现、设计说明、依赖关系、输入输出及时间/内存上界、诊断与异常恢复、测试用例与结果追踪。文档已审核不等于实现已验证。

## 8. MISRA 合规和偏离管理

- 必须先持有合法 MISRA C:2025 规则全文，制定 **Guideline Enforcement Plan**：逐规则适用性、强制程度、工具或人工验证方法、覆盖率与残余风险。
- 规则违规不可静默忽略；每条必须在工具报告中处置，修复或提出正式偏离单。
- 每份偏离记录至少包含：规范条目、受影响版本/源行、必须偏离的原因、风险分析、附加防护、验证方式、审核人与有效期/适用范围。
- 供应商 SDK、生成启动文件、编译器扩展分别形成供应商/第三方软件清单及豁免界面。**不允许整体屏蔽 SDK 告警后宣称整机 MISRA 合规**。
- 合规判定必须准确指出“被分析的代码范围、规则版本、工具覆盖与偏离批准状态”，不能宣传当前项目已经获第三方认证。

## 9. 独立评审与 AI 协作

1. 负责人批准总体标准、关键安全/产品取舍、实体输出许可及正式发布。
2. ChatGPT 提交架构和代码设计合同、测试矩阵、审查清单与风险证据；不得仅靠自己的描述宣称目标测试成功。
3. Codex 仅在已限定工作包下修改约定文件，明确来源/禁止事项与测试命令，提交源差异、构建日志、静态检查和异常测试记录。
4. **AI 写代码与 AI 自评不是独立评审**。安全相关关键变更由负责人或有能力的独立审查者检查，必要时聘请外部专业评审/测试机构。
5. 每次提交必须能追踪：`requirement_id → design_id → source symbol/commit → test_id → raw evidence → review_id`。产品版次、Board 与 Release 同时记录，禁止未经证据推广结论。

## 10. 对现有 V0.1 Host 模板的明确裁定

**审计事实**：原工程只有一个 C11 业务核心、Host 构建/基本测试，无真实 YCT 工程和驱动；CMake 只有常规 GCC/Clang 告警选项，无专业 MISRA 静态分析、覆盖率、软件安全计划和独立评审证据。

- **可以保留**：干净的 Host/ASW 边界、测试入口、物理输出永久禁止约束。
- **必须新增**：本规范、质量门禁、工具基线与 SDK/第三方清单、MISRA 规则执行和偏离登记、评审清单、需求/测试追踪、静态分析及真正 Target 构建路径。
- **严格分类**：代码骨架是 `PROTOTYPE / HOST-ONLY`；绝不能由于补了规范文件就升级成 `AUTOMOTIVE-COMPLIANT`。
