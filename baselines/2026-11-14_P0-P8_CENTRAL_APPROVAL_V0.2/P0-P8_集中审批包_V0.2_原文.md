## 01｜共同生效的产品与安全底线

1. 产品目标是适用于拖挂式房车电控制动系统的电子同步制动控制器，**具体市场、车辆类别、质量/轴数、电制动器及电源范围待核实**。
2. 主控制器独立承担制动决策；App/LCD 只做用户设置、状态、故障和维护交互，不参与实时控制闭环。
3. 两类逻辑输入分别为**制动意图**与**运动信息**；设备/通信方式、作用权重和质量指标未冻结。
4. 用户基础闭环为**重量制动档、制动力等级、状态故障、受控保存和回读**；1–10 级仅作为优先候选，未以 App Mock 或旧代码冻结最终产品档位。
5. 必须区分制动逻辑请求、物理执行许可、驱动实际输出与轮端真实制动效果。
6. 当输入失效、物理故障、车辆工况不同，正确失效动作**不能笼统写作“直接切断最安全”**，须经产品危险分析决定。
7. 当前云途 EVB 仅做无功率、隔离的研发验证。**不允许连接或释放真实拖挂制动功率执行链路。**
8. 旧 GitHub `firmware`、`app` 代码当作不存在，不用来定模块边界、任务顺序或工作完成率；直到未来进入 P5 才决定是否清理或参考复用，不在本包承诺。
9. Variant、Board 和 Release 独立管理，不能把当前开发板当量产 MCU/PCB 已定。

### 03.2 任务执行合同

每一项具体软件修改都必须有**文件/分支范围、来源版本、输入资料、允许变更、禁止变更、测试命令、验收证据和回退策略**。AI 不得将“按 P5 计划开发”扩大为全仓库重构或改变制动安全策略；遇到元件或接口资料缺失应停在受影响边界，不杜撰常量。

### 03.3 测试等级不得混淆

- **DESIGN REVIEW**：职责与契约审查，不能证明可执行。
- **HOST BUILD / HOST UNIT PASS**：桌面逻辑编译测试，不证明目标芯片功能。
- **TARGET BUILD PASS**：指定 MCU/SDK/编译器构建链接，不证明已烧录。
- **FLASH / BOARD RUN PASS**：下载和板载运行的分离证据，不证明外接模块成功。
- **MODULE TEST PASS**：指定型号/接线的实际数据、错误与恢复用例通过。
- **PRODUCT SAFETY PASS**：真实产品工况和物理制动链经受控完整验证；不能由 EVB 代替。

**P5 阶段验收口径：** 范围内模块的批准合同、实现差异、针对正常与异常的测试、精确版本/配置和遗留缺陷齐全；未执行的标记 `NOT_RUN`。

## 05｜P7：系统验证、可靠性与安全验收方案 V0.2

**目标：** 以需求和危险场景为主线，证明实际系统是否满足约定要求，而不是根据代码存在或演示效果判断成功。

| 验证分层 | 对象 | 最小证据及要求 | 不能替代什么 |
|---|---|---|---|
| V0 需求/设计评审 | P2 系统要求、P3 系统设计、P4 合同 | SYS/HA/SG/SSR→验证方法；开放值清单 | 实体运行结果 |
| V1 软件功能验证 | 系统控制、数据质量、参数、HMI 协议 | 审批过的用例、Host/目标测试和错误注入 | 真实功率保护和道路安全 |
| V2 外设/模块验证 | 目标 MCU、实际模块和通信线束 | 电压、时序、通信日志、重启/异常/环境用例 | 轮端制动能力 |
| V3 功率与轮端台架验证 | 目标驱动/电磁制动器、连续/峰值电流、温升和断路/短路 | 受审的独立台架方案、真实量测、保护验证 | 未测试车辆/道路工况 |
| V4 整车及合规验证 | 明确车型/质量/轴数/市场的拖挂组合 | 车辆制动性能、故障工况、环境/EMC、安装与法规证据 | 其它不在适用包络中的车型 |

**需求证据主索引：** `SYS-xxx → SF-xx/DD-xx → HA/SG/SSR（如安全相关） → 测试 ID → 用例版本与工况 → 实测报告 → 缺陷/复测 → 判定`。性能指标 KPI-01～13 必须记录数字来源、工况和测量方法；无阈值则为 `OPEN`，不能判为 `PASS`。

**安全验证专门约束：** 初步危险清单绝非 HARA 或 ASIL 已定；不预设“一故障、一动作”，必须评审非预期制动、制动不足、持续制动、左右/轴间不均衡、欠压/复位、显示误导、无线非法配置、线束错误及应急制动边界。测试设备和人员安全许可独立于文档审批。

**P7 阶段验收口径：** 所有本版本范围内已冻结要求都有证据、评审结论和缺陷处置；安全相关的重大未解风险或空白工况不能以条件批准代替产品通过。

### 3. DD-03｜逻辑制动请求、执行许可与反馈合同

#### 3.1 必须区分的五个层次

1. **制动意图证据**：驾驶员/车端输入是否成立、有效。
2. **系统逻辑制动请求**：在有效输入/参数/状态条件下提出的逻辑需求；可能受限或拒绝。
3. **物理执行许可**：由完整系统和硬件安全条件共同决定；不由单个软件标志自证安全。
4. **执行器命令/物理量**：未来实际功率级的控制量（电流、功率或其他）；当前未冻结。
5. **可观察的执行结果**：实际驱动状态、输出电流/故障和轮端制动效果；具备哪些反馈须基于真实硬件设计。

| 接口语义 | 系统需要表达什么 | 不可作出的推断 |
|---|---|---|
| `logical_request` | 期望制动作用、有效性、来源与生成时刻 | 不等于 PWM、实际电流或轮端力矩 |
| `enable_permission` | 已满足哪些允许条件、有哪些禁止理由 | 不等于硬件上电/失控路径已安全 |
| `actuator_status` | 电源、驱动允许态及可观测的异常 | 不等于必然拥有电流反馈或轮端闭环 |
| `fault_response` | 针对具体危险场景批准的动作/提示/恢复要求 | 不允许无论制动工况都统一写“立即断电” |

**开发板强制条件**：在所有本阶段的实验和演示条件下，真实制动功率输出保持 `NOT_AUTHORIZED`，不得让任何参数命令、通信协议或软件状态改变该条件。

#### 3.2 未来输出准入证据门槛

必须具备目标制动器/供电和电路规格、功率驱动拓扑、上电/复位/棕断默认电气状态证明、危险分析、失效安全响应、故障注入计划以及独立验证审批。**这些目前均不足，物理输出设计保持 `BLOCKED`。**

### 4. DD-04｜系统状态与故障响应合同

#### 4.1 运行状态（语义，非源码枚举）

| 状态 | 进入原因/判据方向 | 对外可报告内容 | 当前控制边界 |
|---|---|---|---|
| `INIT` | 上电、复位、重新检查 | 初始化中、检查结果、版本与必要输入状态 | 未完成准入，EVB 无功率 |
| `INHIBITED` | 未满足基本准入、配置无效或研究平台禁止 | 禁止理由、不可用功能 | EVB 永久禁止真实功率 |
| `READY` | 必要配置/输入和运行准入成立 | 就绪证据、状态更新时间 | 只表明逻辑能力，非物理安全许可 |
| `ACTIVE` | 被认可的制动意图与控制条件成立 | 请求状态、输入质量、有效时刻 | 只表明逻辑请求活动 |
| `DEGRADED` | 经分析允许受限能力的异常 | 功能限制、故障原因、恢复条件 | 是否存在物理制动输出须独立决定 |
| `FAULT` | 已识别且不满足正常运行条件的故障 | 故障标识、告警级别、处置建议 | 不得自动假定某个物理动作最安全 |

#### 4.2 重点事件→状态/后果矩阵

| 事件 | 先确定的行为 | 是否允许自动恢复 | 物理输出与安全责任 |
|---|---|---|---|
| 上电或系统复位 | 报告 INIT，检查必要配置和输入 | 仅检查完成后按条件进入下一状态 | 上电默认物理状态需硬件证实；EVB 无功率 |
| 配置不存在或校验失败 | 标记无效并记录原因，不加载不可信标定 | 需经受控恢复/重新确认 | 不得以预设值绕过安全准入 |
| 输入丢失/过期/矛盾 | 标记相应质量/故障，不再当作正常新鲜输入 | 是否恢复需定义稳定条件 | 真实故障动作须结合制动工况、不能统一拍板 |
| App/LCD 断联 | 明确交互离线或状态过期 | 允许按协议重新建立会话 | 主控制实时环路不依赖手机在线 |

| 维护请求 | 校验权限和当前工况 | 退出条件需定义 | 不能通过维护模式开启 EVB 实际功率 |

#### 6.2 配置事务阶段（重要合同）


a. `RECEIVED`：设备确认收到请求，不表示请求合法。  
b. `VALIDATED`：参数格式、范围、目标对象、版本/权限和允许工况已检查。  
c. `ACCEPTED`：设备已接受执行意图；若禁止更改应明确拒绝。  
d. `EFFECTIVE`：实际生效配置已完成切换，具有可查询的生效版本。  
e. `PERSISTED`：按定义完成可靠保存，可跨上电恢复。  
f. `READBACK_CONFIRMED`：请求方查到的当前有效/已保存内容与设备权威状态一致。

这六个阶段**不得合并成简单的“发送成功”**。若通信中断，只能表达“结果未知/需读回”，不能在 App 上假显示成功；重复和过期请求不能造成不可预期的多次变更；在不适宜工况调参的准入策略留待使用安全评审。

#### 6.3 用户流程

- 首次：核对设备和适用性 → 选择重量档 → 读取建议的默认制动力（来源待标定） → 用户确认 → 查验生效/保存 → 按正式说明在允许场地检查实际驾驶匹配（未来产品阶段）。
- 日常：展示**当前设备确认的重量档/制动力/健康状态**，高频只微调允许项目；无需 App 持续在线。
- 异常：优先提示对驾驶判断有意义的故障及状态有效性，明示离线/状态过期和设备故障的区别。

#### 5. 验证覆盖与度量规则

- **需求覆盖** = 有确定验证计划的批准需求 / 适用的已批准需求（计划覆盖）；

以上是建议度量定义，不能通过分母剔除难测需求来虚增覆盖率。若一个需求需要 Host 与目标板联合证明，两种环境证据缺一不可；不可简单加总重复。
