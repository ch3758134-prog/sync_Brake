01｜共同生效的产品与安全底线

  1. 产品目标是适用于拖挂式房车电控制动系统的电子同步制动控制器，具体市场、车辆类别、质量/轴数、电制动器及电源范围待核实。
  2. 主控制器独立承担制动决策；App/LCD 只做用户设置、状态、故障和维护交互，不参与实时控制闭环。
  3. 两类逻辑输入分别为制动意图与运动信息；设备/通信方式、作用权重和质量指标未冻结。
  4. 用户基础闭环为重量制动档、制动力等级、状态故障、受控保存和回读；1–10 级仅作为优先候选，未以 App Mock 或旧代码冻结最终产品档位。
  5. 必须区分制动逻辑请求、物理执行许可、驱动实际输出与轮端真实制动效果。
  6. 当输入失效、物理故障、车辆工况不同，正确失效动作不能笼统写作“直接切断最安全”，须经产品危险分析决定。
  7. 当前云途 EVB 仅做无功率、隔离的研发验证。不允许连接或释放真实拖挂制动功率执行链路。
  8. 旧 GitHub firmware、app 代码当作不存在，不用来定模块边界、任务顺序或工作完成率；直到未来进入 P5 才决定是否清理或参考复用，不在本包承诺。
  9. Variant、Board 和 Release 独立管理，不能把当前开发板当量产 MCU/PCB 已定。

03.2 任务执行合同

每一项具体软件修改都必须有文件/分支范围、来源版本、输入资料、允许变更、禁止变更、测试命令、验收证据和回退策略。AI 不得将“按 P5 计划开发”扩大为全仓库重构或改变制动安全策略；遇到元件或接口资料缺失应停在受影响边界，不杜撰常量。

03.3 测试等级不得混淆

  • DESIGN REVIEW：职责与契约审查，不能证明可执行。
  • HOST BUILD / HOST UNIT PASS：桌面逻辑编译测试，不证明目标芯片功能。
  • TARGET BUILD PASS：指定 MCU/SDK/编译器构建链接，不证明已烧录。
  • FLASH / BOARD RUN PASS：下载和板载运行的分离证据，不证明外接模块成功。
  • MODULE TEST PASS：指定型号/接线的实际数据、错误与恢复用例通过。
  • PRODUCT SAFETY PASS：真实产品工况和物理制动链经受控完整验证；不能由 EVB 代替。

P5 阶段验收口径： 范围内模块的批准合同、实现差异、针对正常与异常的测试、精确版本/配置和遗留缺陷齐全；未执行的标记 NOT_RUN。

6.2 配置事务阶段（重要合同）

4. 失效与安全验证重点

4.1 当前 EVB 阶段
  • 端口未绑定或模块缺失时，系统不能将空数据判成“传感器有效”；

  • 蓝牙断连不会中断主控的独立控制职责，也不允许手机因断连/重放错误设置；

4.2 未来真实产品阶段（本次禁止宣称已覆盖）

5. 验证覆盖与度量规则

  • 已执行覆盖 = 至少完成一次适用测试的需求 / 适用的已批准需求；

  1. 冻结候选范围：填写具体产品/研究对象、受控源版本、用户和目标硬件；
  2. 审查证据：编译、测试、实物、风险和缺陷逐项对应实际记录；

  4. 评审兼容性：固件/App 协议、参数存储版本、硬件修订和迁移/回滚依据；
  5. 单独获得正式发布批准：本 AI 不能代表负责人签发；
  6. 记录交付和接收：发布包 SHA、交付范围、接收人、遗留风险、缺陷反馈机制；
  7. 进入维护闭环：监控故障，需求/设计受影响时做局部变更分析和回归，不反复推翻有效基线。
