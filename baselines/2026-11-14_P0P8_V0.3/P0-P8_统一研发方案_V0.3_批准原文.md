## 0. 本次修订的核心决策（负责人先看这一节）

### 0.1 三版产品路线正式改为顺序推进

| 产品版本（顺序代号） | 定位 | 必须实现的价值 | 不应混淆的事项 |
|---|---|---|---|
| **V1 / R-TEST：真实功能测试版** | 工程研发与功能验证 | 同步制动控制的关键输入、真实模块、控制、执行及故障观察链路，在相应安全条件具备后**真实可运行、可测量、可复现** | 不是 Host 模拟 Demo，也不是可直接销售或上路的产品 |
| **V2 / R-LCD：LCD 产品交付版** | 第一款正式产品形态 | 在 V1 真实验证的共用制动核心上，较完整地实现原研究资料的 LCD 产品功能，经过真实测试、需求补充、整改回归后完成交付 | 不是只完成显示页面或 LCD 驱动就算交付 |
| **V3 / R-APP：手机 App 产品版** | 后续智能产品形态 | 在稳定成熟的同源制动核心上引入真实 BLE/App 连接、配置、状态、诊断和已选择的智能功能 | 不要求 App 和 LCD 同期首发；不另起一套制动控制算法 |

**产品优先级：** V1 → V2 → V3。三版的正式市场版本号尚未选定；上述 V1/V2/V3 只是顺序代号，不能与 Git Tag、软件 Release 编号或 P 阶段混淆。

### 0.2 当前研发定位

目前**正式产品 PCB 尚未完成**，现阶段只要求建立完整产品技术体系的框架：明确需求、系统功能、接口责任、安全约束、PCB 输入条件、真实模块测试路径以及以后共用的控制能力。不把“框架搭好”写成“V1 测试版完成”。

云途 `YTM32B1LE0-EVB-LQFP64` 是评估与前期实验平台，并不自动代表量产 MCU、最终 PCB 或满足真实功率制动安全。当前开发板**不得直接释放真实拖挂制动功率输出**；未来如要完成 V1 的实际执行验证，必须另外具备经过审查的功率硬件、隔离台架、故障保护与独立测试准入。

### 0.3 P 阶段与产品版次独立

- **P0～P8**：项目立项、现状与可行性、需求、系统架构、详细设计、实施、集成、验证、发布与维护的**研发过程**。
- **V1/V2/V3**：依次实现的**产品版本目标**。各版本在受影响范围内均需要相应的 P2～P8 活动和证据；不是 V1 走完所有 P 阶段就永远不用做 P7。
- **Variant / Board / Release**：产品功能配置、硬件板型、发布版本三套独立配置维度；LCD 与 App 可以共享逻辑和接口，但产品发布时间不同。
- 原 V0.2 的 P8 `R0/R1/R2` 是**样件/工程/产品发布成熟度**的历史分类，不是本次 V1/V2/V3 产品版次。为避免混淆，本稿后续称**研究验证、工程验证、产品交付**三个证据等级。

### 0.4 对旧 P0–P8 V0.2 的影响

| 事项 | V0.2 的有效内容 | V0.3 的修订决定 |
|---|---|---|
| P0–P4 基础体系 | 产品定位、主控独立、系统需求、SF/HA/SG/SSR、DD-01～08 已批准 | **保留**；新三版路线替换任何“LCD/App 同期首发”的理解 |
| P5 开发顺序 | W1～W5 能力工作流，未绑定明确产品版次 | **调整**为 V1 实际模块及共用核心优先 → V2 LCD → V3 App；旧代码不作起点 |
| P6 集成顺序 | I0～I4 通用分级 | **调整**为每个版本分别进行相应集成，V1 首先证明模块和受控同步制动链路 |
| P7 验证重点 | V0～V4 分级与安全追踪 | **调整**为 V1 真实功能验证、V2 完整 LCD 产品/车辆工况验证、V3 App/通信回归验证；不能跨版挪用验收结论 |
| P8 发布管理 | 样件/工程/产品发布等级与完整交付门槛 | **调整**为三版各自定义交付类型和发布基线；V1 内部测试不称销售产品，V2 首个正式产品交付 |
| 当前工作 | 已批准设计，产品数据及执行证据开放 | **优先搭框架和 PCB 前置设计输入**，不提前宣布软件/实板/车辆试验完成 |
| GitHub 旧代码 | 既有 `firmware`、`app` 排除为研发基线 | **继续视为不存在**；不保管、不维护、不据其决定方案；将来实施阶段才决定清理或复用 |

## 1. P0｜项目定位与版本目标（修订后有效）

**项目长期目标：** 形成可实际产品交付、可制造、可靠、可维护、成本可控的拖挂式房车电子同步制动控制系统，而不是完成一块开发板 Demo。

### P0 的成果和准则

1. 制动主机独立承担自动同步制动判断；LCD、App 是交互形态，不是实时安全制动闭环的必需参与者。
2. 共用核心控制能力服务于 V1、V2、V3，允许不同 MCU、PCB、LCD、蓝牙模块演进。
3. 研发策略首先取得**真实模块与同步制动功能证据**，再产品化 LCD，最后扩展 App。
4. 负责人决定产品取舍、架构和验收；ChatGPT 承担研究/设计和技术审查，Codex 只按明确范围执行经授权的代码任务。
5. 三版产品都以需求、设计、实现、测试和版本证据可追踪为基本要求。

**P0 当前判定：** 项目定位、组织方式已获此前批准；本次新增的是版本优先级与首发产品形式。无需重新立项。

## 2. P1｜事实基线与可行性范围

### 当前能确立的事实

- 目标为电控制动器拖挂式房车同步制动系统，首版具体市场、质量范围、轴数、轮端制动器与电源参数未冻结。
- 有云途 `YTM32B1LE0-EVB-LQFP64` 开发板相关资料，最终 PCB 尚未设计完成。
- 有 BMA510、蓝牙等器件/模块历史资料，但**实际安装的加速度模块、CAN 设备与蓝牙模块的精确型号、接口和固件协议必须按实物核实**。
- 曾研究普通 LCD 及智能 App 功能，相关来源见本稿第 9 节。LCD 正式屏幕规格、实体按键及安装结构尚未确定。
- **现有 GitHub firmware/app 源码不属于新的工程资产基线**；不依据它们计算完成率，也不预设复用。

### P1 后续需要补齐的证据

目标销售地域和车辆类别、牵引车供电及制动信号、轮端电制动器规格与电流、电气线束与应急制动关系、传感器模块与通信协议、研发板实物/手册匹配、正式产品 PCB 约束。

**P1 当前判定：** 已批准现状报告，证据缺口继续追踪；不得把资料拥有视为实物功能可用。

## 3. P2｜系统需求与三版功能分配

已批准的 P2 系统需求方向（58 条候选体系及 OD-01～09 待决）仍有效。现在需给需求增加“适用产品版本”“需完成的测试证据”两个维度，避免把可选功能提前放进 V1。

### 3.1 三版功能分配总表

| 系统能力 | V1 真实功能测试 | V2 LCD 交付 | V3 App 产品 |
|---|---|---|---|
| 制动意图识别、有效性与超时 | **真实输入验证** | 保留并产品级验证 | 同源复用、回归测试 |
| 运动/加速度信息与质量判断 | **真实模块/链路验证** | 根据安装和标定完成产品验证 | 同源复用、回归测试 |
| 同步制动核心逻辑与受限请求 | **完整基础功能与异常验证** | 完成标定和交付验收 | 同源复用、不另起核心 |
| 功率执行、反馈、保护 | 受控台架验证，需独立安全准入 | 真实产品电路/轮端/工况完整验证 | 不改变已验证执行安全边界 |
| 重量制动档与制动力等级 | 提供必要测试参数输入和状态核对 | **LCD 完整本地交互和可靠保存** | 复用语义，由 App 读写/回执 |
| 状态、故障、恢复与版本 | 基础诊断及真实故障观察 | **LCD 显示/提示及维护要求** | App 提供连接、诊断与状态新鲜度 |
| 实体 LCD、按键和菜单 | 非 V1 完整交付条件 | **V2 核心要求** | 可与 App 变体共用，不强制同机并存 |
| 蓝牙硬件和通信 | 如属已选模块，可先做真实通信验证；不要求手机 App 产品 | 不作为 V2 交付依赖（除非产品配置专门选定） | **真实 BLE/App 全流程** |
| 手机 App UI、连接与配置 | 不作为产品交付要求 | 不作为 LCD 版必须功能 | **V3 核心要求** |
| Boost、手动制动、OTA、侧摆辅助等 | 不默认包含 | 从 LCD 原始功能池逐项评估并确定范围 | 按智能版产品决策新增或复用 |

### 3.2 第一版 V1 的“基础功能”不能降级为纯软件骨架

V1 最终目标应包含制动触发、运动输入、控制判断、执行与诊断的**真实功能证据**，不能只证明接口函数已写、Host 测试 PASS 或模拟 UI 可运行。但在当前 PCB 未完成的阶段，只要求提前准备这些功能的需求、边界、验证方法及必要的系统接口框架；**V1 实际交付判定必须等待真实条件具备**。

## 4. P3｜系统架构、产品边界与风险

继续采用已批准的 SF-01～SF-09 系统功能分配、PE-01～PE-06 首版方向、KPI-01～KPI-13 指标目录，以及 HA-01～HA-12、SG-01～SG-08、SSR-01～SSR-18 初筛结果。此次更新其产品版次依赖。

| P3 系统层内容 | 三版共用关系 | 当前必须解决的设计问题 |
|---|---|---|
| 输入与质量评估 | V1 首先验证，V2/V3 共享 | 信号来源、单位、方向、时间有效性和失效状态 |
| 控制策略及逻辑制动请求 | 版本共用核心 | 制动意图、运动信息的角色与控制限制；具体控制律须另研究和验证 |
| 真实执行/保护 | V1 台架研究、V2 产品化，V3 不另起一套 | 功率级、电流/温度、复位默认态、独立禁止/诊断和故障处理 |
| 参数/状态/诊断模型 | 共用 | 制动档与微调的独立语义、保存版本、故障状态和 HMI 一致性 |
| LCD、App 表现层 | 基于统一系统状态和参数合同 | V2 LCD 先交付；V3 App 后开发，不能反过来驱动核心设计 |
| 功能安全与车辆适用性 | 每一产品版本按实际硬件/工况审查 | 输入失效、非预期制动、制动不足、无法释放、不均衡、显示误导等危险 |

### P3 关于制动安全的重要边界

- 不能从“制动请求已计算”推断“允许真实 PWM/电流输出”。
- 不能假定所有故障都应立即取消制动力；响应需结合车辆工况、执行器类型、正在制动还是未制动来分析。
- 对于尚未确认的市场、制动器、路况、轴数，不编造 ASIL、性能阈值或法规符合性。
- 当前 EVB 仅用于研发验证；任何真实制动功率须独立硬件安全方案、台架许可和证据。

**P3 当前判定：** 概念架构批准、开放物理参数；按当前 V1/V2/V3 的顺序进一步分配设计与验证工作。

## 5. P4｜系统详细设计及当前要搭的“框架”

沿用已批准 DD-01～DD-08 系统合同，不重做既定架构。**当前优先完成框架与设计输入，而不是实现一个假定 PCB 已经存在的完整产品固件。**

### 5.1 八项系统设计合同

| DD 编号 | 系统设计内容 | 当前应交付的框架成果 | 还不能冻结的事项 |
|---|---|---|---|
| DD-01 | 产品适用范围 | 产品适用/排除条件表、各版适用范围 | 市场、质量、轴数、法规 |
| DD-02 | 外部输入 | 制动触发与运动输入语义、时效、质量与异常合同 | 精确电气、信号源、传感器参数 |
| DD-03 | 输出与执行保护 | 逻辑请求、物理许可、实际执行、故障反馈的职责边界 | 最终功率 PCB、关断路径、额定输出 |
| DD-04 | 运行状态与故障 | INIT、INHIBITED、READY、ACTIVE、DEGRADED、FAULT、SERVICE 的系统含义；异常场景 | 所有真实故障下的物理制动动作 |
| DD-05 | 性能预算 | KPI 定义、量化证据的获取路径与测试工况 | ms、A、V、温度等无依据数值 |
| DD-06 | 配置与 HMI | 重量档/微调、生效/保存/读回、LCD 与未来 App 的统一用户语义 | 重量区间、默认值、应用时机与算法映射 |
| DD-07 | 安全责任与验证 | HA→SG→SSR→责任子系统→计划证据 | 正式 HARA、产品安全结论 |
| DD-08 | 产品配置与维护 | Variant/Board/Release、诊断、版本兼容、维护责任 | 最终型号、配套硬件版本 |

### 5.2 框架的正确深度

**本阶段应明确：** 产品功能模块与责任、模块间数据及状态语义、公共控制与 HMI 的隔离、输入/输出边界、诊断、版本管理、PCB 前置要求以及对应验证路径。

**本阶段不强制：** 按尚未确认的正式 PCB 定死 MCU 引脚/时钟、推定 CAN 帧/蓝牙 UUID、决定输出电路、完成正式 LCD 页面和 App 代码、写满所有厂商外设驱动。后续若经独立任务授权建立软件结构骨架，也必须基于真实 SDK/资料，不以旧 GitHub 代码为依据；构建或模拟运行不能冒充模块实测。

### 5.3 PCB 开发前必须交付的系统输入

| 子系统 | PCB 设计前必须写清的接口与限制 | 依赖证据 |
|---|---|---|
| 供电与电气 | 牵引车/拖挂供电、工作/瞬态、反接/欠压/浪涌、接地与线束防护 | 车辆拓扑、目标市场与实车/供应商依据 |
| 制动输入 | 触发来源、接口电平/隔离、诊断与异常识别、故障时受控行为 | 真实车辆信号与风险分析 |
| 运动输入 | 传感器位置、安装方向、接口类型、数据质量和可观察故障 | 实物模块与系统算法需求 |
| 功率执行 | 单/多通道及轮端负载、驱动/反馈、电流/温度、电气保护、独立输出禁止 | 实际电制动器规格与危害分析 |
| MCU/通信 | 外设资源需求、调试、看门狗、CAN/UART/I²C/必要拓展 | 经确认的功能和模块接口 |
| LCD/HMI | 显示内容、按键逻辑、故障优先级、安装和人机操作条件 | V1.1/V2.6/V3 功能矩阵及整机方案 |
| 生产与测试 | 生产测试、版本身份、故障注入、隔离测试点、维护接口 | P6/P7 测试场景与安全边界 |

## 6. P5｜实施开发与模块测试：按 V1 → V2 → V3 组织

P5 只在相关 P4 合同、硬件/接口证据和具体实施授权具备后，对相应模块开展实现。**这不是本稿批准 Codex 立刻修改代码的许可。**

### P5-A：V1 真实功能测试版工程

1. 建立独立于旧 GitHub 代码的新工程实施基线，清楚界定共用核心、板级适配、设备通信、系统诊断与测试边界。
2. 在真实官方 SDK 和开发板版本确认后逐个完成启动、时基、必要 GPIO/CAN/UART/I²C/定时器等外设接入；仅实现与已确认真实模块相关的能力。
3. 接入实际制动意图来源和运动模块，得到可观察的原始数据、单位/坐标、错误和超时事实。
4. 实施同步制动逻辑和系统状态、参数、诊断；建立可重放的工况测试和确定性的异常路径。
5. 有硬件安全准入前，只能用隔离/无功率测试路径研究执行请求；有功率硬件和隔离台架审查后，才允许开展受控实物执行测试。
6. 保留蓝牙等相关模块的物理通信验证路径，但不要求 V1 制作可发布手机 App。

**P5-A 的退出证据：** 明确代码版本与工具链、Host/Target 构建、实际烧录、模块真实数据和异常用例（各自分别记录）；对实体执行未取得许可的场景必须标 `BLOCKED/NOT_RUN`。

### P5-B：V2 LCD 交付功能

先由第 9 节 LCD 研究功能矩阵决定功能清单，再完成屏幕和实体操作、菜单、参数存储、故障显示、安装/维护等能力；在真实产品 PCB 和轮端执行条件下补齐系统级验证。不因 LCD 可显示状态就宣称轮端制动行为正确。

### P5-C：V3 App 产品

在稳定成熟的制动核心和设备参数/状态合同上新增 BLE/手机 App 真实连接、权限、读写确认、状态新鲜度和经批准的智能功能。与 LCD 保持控制语义一致，不复制控制算法；是否与 LCD 同机共存另由 Variant 决定。

## 7. P6｜系统集成与真实模块联调

| 集成层级 | V1 重点 | V2 重点 | V3 重点 |
|---|---|---|---|
| I0：合同一致 | 输入单位、时效、状态、参数结果 | LCD 交互与真实设备一致 | BLE/App 与设备一致 |
| I1：外部模块 | 传感、CAN/UART/蓝牙相关物理设备（以实物配置为准） | LCD、按键、参数存储、诊断 | 手机、蓝牙协议、安全回执 |
| I2：控制逻辑 | 制动触发、运动输入、控制请求、故障状态整合 | LCD 操作不破坏控制闭环 | App 断线/重连不影响独立同步制动 |
| I3：无功率整机 | 在物理输出隔离条件下联通整个制动逻辑链 | 真实 UI 结合系统状态完整联调 | 真实手机－设备全业务链路联调 |
| I4：受控功率/实体系统 | **仅安全准入通过后**在受控台架验证实际执行 | 产品目标硬件、电磁制动器、环境/故障工况集成 | 对已交付核心的功能/安全回归验证 |

每次集成记录版本、硬件修订、输入/预期/实测、日志、缺陷、复测和安全条件。V1 的真实模块验证不能凭 Mock 替代；V2 的 LCD 完整联调不能凭静态 UI 截图替代；V3 的蓝牙不能凭单纯串口字节通证明 App 业务链路。

## 8. P7｜分版验证与产品实际交付标准

| 产品版次 | 验证目标 | 必须证明的具体结果 | 不得当作通过的证据 |
|---|---|---|---|
| V1 测试版 | 基础同步制动及各选定模块的真实功能 | 实体输入采集、控制与诊断可观测、经准入的实际执行响应；必要故障注入；版本和测试工况可复现 | 只有 Host PASS、开发板 LED/串口显示或输出 API |

## 9. V2 LCD 功能研究资料与逐项范围（重要新增）

### 9.1 本稿实际核对的历史资料

3. `RV_Brake_V3.docx`：基础闭环“制动档＋制动力＋状态＋保存”，LCD 主屏、直接调节与菜单，选配增强/手动/智能管理/侧摆等功能清单。

这些资料属于**功能设计依据**，不代表所有候选功能都由负责人选为 V2 必做，也不替代真实制动性能标定。

### 9.2 LCD 功能矩阵（V2 开发前的范围判定）

| 功能 | 历史资料语义 | 本稿建议分级 | 需要后续确认/测试的重点 |
|---|---|---|---|
| 主控独立自动同步制动 | 基础共同功能 | **V2 必需，来自 V1** | 控制行为、受限/故障、安全与实际性能 |
| 重量制动档 | 匹配房车重量范围 | **V2 必需** | 适用重量/档数、选中/确认/保存、参数合法性 |
| 同档制动力微调 | 高频的强弱调整（1～10 为候选表达） | **V2 必需** | 档内独立、边界、调参许可与用户提示 |
| LCD 主界面 | 当前制动档、制动力、工作状态 | **V2 必需** | 有效状态与过期/未就绪/故障显示 |
| 实体直接操作 | 增加、减小、菜单/选择、确认、返回 | **V2 必需** | 消抖、操作一致性、驾驶中误操作控制 |
| 状态与故障 | 正常、制动中、异常优先提示 | **V2 必需** | 线路、电源、过流/短路、能检测的附加故障 |
| 参数保存及重新上电 | 受控保存与恢复 | **V2 必需** | 生效/持久化/读回分开，掉电/版本错误可诊断 |
| 恢复默认 | V2.6 标为建议，V3 列入菜单 | **V2 重点评估，待正式列入清单** | 恢复哪些用户值，不误擦标定或故障数据 |
| 起始/最小制动力 | 高级制动调节 | **候选增强** | 体验需求、控制律、标定、安全影响 |
| 正向响应调节 | 前进制动灵敏度 | **候选增强** | 工况与验证要求 |
| 倒车响应 | 反向独立设置 | **候选增强** | 倒车信号、响应必要性与安全 |
| Boost | OFF/B1/B2/B3 等例子 | **候选增强** | 各级含义、上限、误触发风险 |
| 简单/高级模式 | 高频简洁、细参数进菜单 | **候选增强** | 配置一致性与误操作 |
| 手动独立制动/手动预设 | 需要明确操作和安全边界 | **高风险候选，单独审查** | 实体操作、故障保护及车辆安全 |
| 停车保持 / 自动手动模式 | 特殊工况功能 | **高风险候选，单独审查** | 正确车辆工况及与应急制动关系 |
| 亮度、语言 | V2.6 仅在需要时加入 | **可选** | 显示与 BOM/区域配置 |
| 多套配置 | 不建议作为 LCD 基础 | **不默认纳入** | 选配后才设计配置结构与切换权限 |
| OTA、车机与详细无线管理 | 主要属于 App 智能管理 | **不作为 V2 LCD 必需** | V3 再确认 |
| 侧摆稳定辅助 | 基础同步制动外独立增强 | **独立功能课题** | 传感器、稳定性模型和安全验证 |
| LCD 屏幕、按钮、外壳与安装 | 原文保留整机侧选择 | **V2 交付必须最终选定** | 真实 PCB、HMI BOM、环境与可制造性 |

**V2 范围冻结方式：** 先完成此功能矩阵的具体产品取舍，再分批实现与实测；“尽量完整复现 LCD 功能”应被理解为覆盖原资料所研究的**基础功能与需要评估的增强池**，但不能不经需求和安全判断就把所有选配项当成强制功能。
