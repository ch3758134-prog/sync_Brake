## 0. 给负责人看的审阅摘要

**P2 解决的不是“代码怎么写”，而是：真实产品要完成哪些用户任务、在什么条件下工作、发生异常时应当怎样表现，以及如何证明需求被实现。**

在 P0/P1 已批准的边界下，本稿建议将以下作为**核心系统需求候选**：

1. 主控制器独立执行自动同步制动；手机与 LCD 仅承担交互/诊断/配置，不是主制动实时决策依赖。
2. 形成“**制动档（匹配房车重量）＋制动力等级（同档内微调）＋状态/故障信息＋参数受控保存**”的基础用户闭环。
3. 对制动触发信号、运动/减速度信息、参数和执行状态建立可信度、有效性、失效与恢复约束；但**不预先选死 CAN、I²C、某一传感器或控制算法**。
4. 制动执行的启用、上电默认状态、异常降级/关断及恢复必须由后续危害分析、实际硬件设计和系统验证共同确定；**当前开发板阶段绝不开放真实制动功率**。
5. 形成可跨 MCU/板卡和不同 HMI 复用的系统需求，保证 Variant / Board / Release 独立可追溯。
6. 蓝牙与 App 用于特定 Variant 的设备连接、设置、回读与诊断；未经共同协议、身份校验和安全约束验证，不允许将真实写入联到制动控制链。

**P2 现阶段不能冻结：**目标市场/法规、首款 Variant、适用拖挂质量/轴数/电磁制动器配置、实际电压范围、制动触发来源、加速度模块实物型号及通信方式、CAN 是否参与核心控制、BLE 真实协议、档位数量/重量范围、等级到输出映射、量化时序/精度与故障安全动作。这些保留为可追踪的待决项，不能被代码或历史示例偷换成批准事实。

**本阶段的批准含义**：认可基础用户任务、系统需求方向、需求边界和待决事项的处置顺序；不代表冻结所有 `TBD` 数值，更不代表实现、Target Build 或安全验收通过。

## 2. 利益相关者与实际使用场景

### 2.1 相关方及其真实需要

| 相关方 | 核心需要 | P2 应形成的需求方向 |
|---|---|---|
| 房车驾驶/使用人员 | 首次设置易理解，正常驾驶不需要持续操作手机/屏幕，遇异常能知道设备状态 | 制动档、制动力设置，主机独立工作，简洁状态与故障提示 |
| 安装/维护人员 | 能核对连接、电源、传感与执行接口，发现故障可定位问题 | 可诊断、可识别配置与版本，安装检查与检修安全路径 |
| 项目负责人/研发者 | 能修改 MCU/HMI 而复用控制系统，理解代码行为并验证 | 清晰功能边界、测试追溯、配置/版本独立、受控参数 |
| App/LCD 使用方 | 操作语义一致、反馈准确，链路故障不误导用户 | 统一状态与参数语义、命令结果回读、断线提示 |
| 故障/安全审查相关人员 | 任一正常/异常路径有明确状态和可重复的验证证据 | 危害分析、执行允许条件、可测异常响应、故障注入 |

### 2.2 场景目录（系统需求的直接上游）

| 场景 ID | 场景与用户期望 | 重要异常/边界 | 主要关联需求组 |
|---|---|---|---|
| `SC-01` | 首次安装/上电：设备有清楚的启动状态，未完成必要检查前不能误认为已可制动 | 复位、缺失配置、版本不符、硬件未就绪 | `SYS-INIT`, `SYS-SAFE`, `SYS-DIAG` |
| `SC-02` | 首次配置：用户选择房车重量制动档，再设置制动力等级，系统给出结果并保存 | 输入越界、未确认保存、未读回成功 | `SYS-CFG`, `SYS-HMI` |
| `SC-03` | 正常驾驶：用户操作牵引车制动，主控依据已确认的有效输入与参数独立决定拖挂制动请求 | 驾驶意图/减速度源质量变化、瞬断、采样过期 | `SYS-IN`, `SYS-CTRL`, `SYS-SAFE` |
| `SC-04` | 行驶中微调：仅调节制动力等级，不改变制动档，且能识别设置是否实际生效 | 重复命令、非法命令、超范围或不合适工况 | `SYS-CFG`, `SYS-HMI`, `SYS-COM` |
| `SC-05` | 停车/再次启动：安全地恢复已确认的有效配置，或给出明确未就绪状态 | 存储损坏、版本升级、部分写入、电源异常 | `SYS-CFG`, `SYS-SAFE` |
| `SC-06` | App 连接/断开：用户查看状态并调整设置；手机离线后主控仍按系统规则运行 | 假设备、配对失败、失联、命令丢失、回执不一致 | `SYS-COM`, `SYS-HMI`, `SYS-SEC` |
| `SC-07` | 状态异常：用户收到符合严重程度的提示；维修人员可识别故障与发生条件 | 故障抖动、错误恢复、日志缺失、无法区分未连接与设备正常 | `SYS-DIAG`, `SYS-SAFE` |
| `SC-08` | 外设验证：工程师在云途开发板连接蓝牙/加速度模块，验证接口与数据，不牵连真实执行功率 | 接线错误、电平不适配、传感数据无效、CAN Bus-off | `SYS-LAB`, `SYS-IN`, `SYS-COM` |
| `SC-09` | 产品配置切换：不同 MCU/Board/Variant 复用控制语义，测试证据不会跨板误认 | 引脚冲突、驱动差异、配置混装、发布版本不一致 | `SYS-PLAT`, `SYS-DIAG` |
| `SC-10` | 真实产品集成：未来接入电磁制动器与功率驱动前必须满足单独的系统/硬件安全准入 | 上电、掉电、看门狗、驱动失控、供电波动、错误制动输出 | `SYS-OUT`, `SYS-SAFE`, `SYS-QUAL` |

**场景边界**：使用案例是用户任务及期望结果，不是 UI 页面/驱动名称。比如 `SC-03` 不预先要求加速度由 I²C BMA510 获得，也不宣称 CAN 必须来自牵引车。

## 3. 系统与外部环境边界

### 3.1 逻辑边界

```text
[牵引车制动相关输入]     [运动/减速度相关输入]
            \                 /
             \               /
              [BrakeSync 主控制器]
              | 信号与状态评估 |
              | 制动策略与请求 |
              | 参数、故障诊断 |
                /           \
       [HMI/App]       [功率执行与制动器]
     设置/查看/维护        （未来独立安全准入）
```

- `BrakeSync 主控制器` 是自动制动控制职责主体；**手机、LCD 和云端不参与必须实时闭环**。
- `外部输入` 至少包含制动意图/触发信息和运动相关信息的**逻辑概念**；哪些是主输入、冗余、辅助或可选须经 `OD-02` 决定。
- `功率执行` 属产品长期范围，但现有 EVB 没有受控的实际制动功率执行方案；不得将目标输出 API 已存在视为硬件准入。
- `接口技术`（CAN、I²C、UART、BLE）及 `软件分层` 是后续设计/实现约束，并非所有产品 Variant 的无条件系统需求。

### 3.2 初始产品配置管理逻辑

- **共用核心**：输入质量、系统状态、配置语义、制动请求边界、故障与验证语义尽量相同。
- **Variant**：决定是否有 LCD/App、可选功能、用户交互/诊断能力；不暗中改变共用语义。
- **Board**：决定目标 MCU、引脚/电源/通信外设、硬件关断路径；当前 `YTM32B1LE0-EVB-LQFP64` 是**验证板**，不是量产 MCU 冻结决定。
- **Release**：标识系统软件/协议/配置及适用板型的发布；不得将固件和 App 任意组合宣称兼容。

### 5.2 安全、网络和合规的处理原则

- **功能安全**：P2 识别危险源与需求主题，后续必须建立适合目标车辆场景的危害分析和执行安全要求分配。本文**不是 HARA、ASIL 判定或安全案例**。
- **安全状态不能空泛**：例如“传感器故障直接切断制动力”是否安全须考察正在制动/未制动、道路工况、执行器模式与其它可用信息，不能全局拍板。
- **网络/配置安全**：与制动相关的写操作在身份、完整性、授权、回执、超时和冲突机制未确认前，不连接真实执行链；App UI 演示可使用 Mock。
- **法规与认证**：目标市场/车辆类别尚未确定，不能宣称已符合特定标准；产品阶段必须确认适用法规、试验和责任分工。
- **当前研发禁令**：开发板阶段只做无功率输出的功能验证，不允许借 P2 的任何候选要求释放真实制动功率。

| 实时控制主机 | 输入评价、控制请求、参数/状态/诊断、安全允许 | Host 模拟工况、逻辑边界、异常路径 | 不能以 Host PASS 证明实际制动效果 |
| 目标 MCU/板级适配 | 实际外设接入、计时、引脚/时钟/中断 | YTM32B1LE0 EVB 上 UART/CAN/I²C/GPIO 等适用接口 | RevA/RevC 文档须与实物、SDK 核对 |
| 外部运动/蓝牙模块 | 硬件采样和无线通信 | 模块身份、供电、线序、单模块原始数据采集 | BMA510 芯片手册不能证明 CAN 模块类型 |
| App 或 LCD | 用户配置、状态、故障查看 | Mock UI、交互状态、协议状态回显 | 不能把 App 设置动作当作已写入 MCU |
| 执行/功率硬件 | 输出转换、驱动、电流/温度保护、硬件禁止 | 未来先进行原理图论证与隔离台架测试 | 当前 EVB 无实际功率执行授权 |
| 配置/版本工程 | 需求、Board/Variant/Release、测试记录追溯 | Git HEAD、CI、版本标签、设备身份 | `management` 分支不会自动进入 firmware/app 工程工作树 |

### 6.1 当前存在的具体硬件资料冲突

- 已找到 `SCH_YTM32B1LE0_EVB_Q64_RevC.pdf`（5 页）与 `YTM32B1LE0-EVB-LQFP64评估板参考手册.pdf`（RevA、16 页）；原理图所示 MCU 为 `YTM32B1LE05H0VLHT`，但**用户实物 PCB 修订版/顶标尚未核对**。
- 参考手册将板载 EEPROM 总线标作 `I2C0`，RevC MCU 管脚标注显示 `PTD0/PTD1` 关联 `I2C1` 的复用功能，需回到正确芯片官方 pin mux 和真实板卡修订核对；绝不能直接照旧手册指定 SDK 驱动实例。
- BMA510 原厂数据手册已读取，**但用户拿到的加速度模块是否 BMA510、模块板电平、是否 CAN/I²C 等都不能凭此推断**。
- WLT8016 等蓝牙模块曾在历史对话中列出，所购实物准确型号和完整软协议仍未核对；目前不填写 AT/GATT UUID 等猜测数值。

### 6.2 研发验证与产品需求之间的关系

为了不等待最终 PCB，允许继续开展可被独立评估的**验证板功能研究**，例如 UART、CAN、外接传感器数据读取、蓝牙字节层、状态/参数 Host 测试。这些任务应有独立的任务许可、接线/安全检查和实测记录，不意味着所有系统需求已签发给 Codex，也不意味着真实制动输出得到授权。

### 9.2 允许与不允许的 P2 结论

**允许**：负责人批准本稿描述的**系统需求框架和基础功能方向**，把真实硬件条件、协议、数值和可选功能作为有明确责任与去向的待决项；后续依据已批准条目形成系统架构/接口设计候选。

**不允许**：将 P2 批准写成“所有需求已冻结”“产品满足安全标准”“已完成实车性能指标”“可以打开输出”“已取得蓝牙 GATT 数据”“APP/MCU 开发已完成”。

**正式需求冻结的补充条件**：关键 `OD` 决策有审批，相关的定量需求有来源/工况/验收阈值，需求版本可追溯；如果范围改变，修订受影响条目即可，不必重新推翻整份 P0/P1。

### 9.3 建议在本次审阅中重点关注

1. 是否认可**共用核心主机独立控制**及“制动档＋制动力＋状态＋受控保存”的基础功能闭环？
2. 是否认可当前只冻结**逻辑需求**，暂不将 CAN、BMA510/WLT8016、MCU 和 BLE 协议作为最终产品的刚性配置？
3. 对手动独立制动等增强功能，是否仍以**按 Variant 单独批准**为准？
4. 是否接受所有实际功率输出的安全论证与测试作为独立且不可跳过的前置条件？
5. 哪些 `OD` 需要优先补证，尤其是 `OD-02/03/05/09`？
