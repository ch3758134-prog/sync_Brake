## 1. P0-01｜立项背景、产品目的与定位

### 1.1 现实问题

拖挂式房车与牵引车通过牵引装置连接，双方质量、载荷、制动器特性与响应并不相同。制动过程中若拖挂端响应不足，可能增加牵引装置的前推趋势；若制动力过大，则可能形成拖拽、附着利用不当等风险。系统需面向真实道路使用中的制动协调问题，而不是仅把一个传感器读数转换成 PWM 输出。

项目目前具备历史方案、嵌入式驱动与主控软件骨架、App 模拟界面等研发资产，但这些成果既不能证明已满足产品级要求，也不能替代项目目标与开发边界的正式决定。

### 1.2 候审的项目目的

> 研发面向拖挂式房车的 BrakeSync 电子同步制动控制系统，形成可用于真实产品持续开发、验证和交付的共用制动控制技术平台。平台在满足安全和法规适用要求的前提下，兼顾制动协调性、可靠性、可维护性、产品扩展能力和批量成本，并通过配置形成不同产品形态。

项目目的分为两层：

- **产品层**：提供可实际安装、配置、诊断和维护的拖挂式房车同步制动控制产品能力。
- **研发平台层**：积累可复用的控制软件、基础软件适配、硬件设计、接口定义、验证方法和配置/发布体系，避免每换一种 MCU 或 HMI 就重新开发整套产品。

### 1.3 产品与应用对象

- **主要用户（候选）**：拖挂式房车驾驶/使用人员；围绕安装、检查、维修和售后服务的人员。具体销售对象、区域和使用资质尚未确定。
- **被控对象**：拖挂式房车制动执行机构；当前历史方案以电磁制动器为主要研究方向。最终制动器类型、数量、轴数、额定条件待后续需求和硬件确认。
- **运行原则（已体现于历史产品方向）**：主控制器承担正常自动制动所需的实时控制职责；App/LCD 面向设置、状态和故障交互，正常制动不依赖手机始终在线。
- **产品形态**：可配置的主控、HMI、通信和车辆信息扩展组合；首发产品具体配置**尚未决定**。

### 1.4 项目不是以下几种单独成果

不是云途 MCU 开发板 Demo，不是仅供展示的 Flutter 页面，不是一个独立 BLE/CAN/IMU 驱动库，也不是未经确认即可用于实际拖挂制动的原型。各项可以是验证或迭代资产，但不能代替系统产品的交付目标。

## 3. P0-03｜高层范围、边界与交付责任

### 3.1 纳入项目的总体范围

1. **产品/系统工程**：实际使用场景、需求、功能分配、架构、约束、配置与追溯。
2. **控制器软硬件**：电源、输入采集、MCU、基础软件、执行与保护、诊断及整机工程化。
3. **制动控制软件**：信号质量与运动状态处理、控制逻辑、参数管理、运行状态、异常与恢复机制。
4. **设备与通信**：与加速度计、CAN 相关信息源、BLE 等外设或扩展链路的实现和验证；是否采用某个具体接口、模块或信号，由后续论证决定。
5. **人机交互**：根据产品 Variant 提供 App 或 LCD/实体操作的设置、状态、诊断交互；多形态共用核心语义。
6. **集成与验证**：Host/Target 软件测试、实板驱动、通信与执行链验证、故障注入及系统/产品级验证。
7. **产品化支持**：配置管理、制造测试、故障服务、维护、升级与迭代所需的适用能力。

### 3.2 此时不承诺的内容

以下**不是被否定的功能**，而是尚未形成有效产品范围决策的事项：

- 首款产品是否同时具备 LCD 与 App；是否覆盖 Android 和 iOS 双平台；具体屏幕/按键/车机交互。
- 手动拖挂制动、OTA、侧摆辅助、多辆房车配置等高级功能是否纳入某一发布。
- 重量档位数量及区间、制动力等级的实际映射、预设值、参数上下限和标定方法。
- 目标 MCU、开发板、CAN 来源、传感器、BLE 模块及其协议、电磁制动器适配范围。
- 电源电压范围、兼容车型/市场、认证/法规路径和首发量产时间。

其中，历史用户功能方案和 App 要求中出现的 **1–10 级制动力表达**属于当前重要的用户交互候选，不能直接当作控制输出的物理量、标定结果或最终需求冻结值。

### 3.3 系统边界的高层认识

系统的正常工作涉及牵引车制动信息/车辆状态、BrakeSync 主控制器、拖挂制动执行机构、必要的供电和操作/维护接口。具体信号获取方式、数据可信度、失效语义及车辆兼容性必须在后续需求与系统设计中定义。

**安全边界**：任何实际制动输出应先满足硬件、软件与系统安全要求，并通过对应层级验证。不能因为软件输出函数存在或 Host 测试通过就释放实际功率。在故障时应采用何种安全状态，必须结合行驶工况和危害分析确定，**不能未经分析就假定“所有故障一律断开制动力”必然安全**。

### 3.4 产品配置和软件发布的概念边界

- **Variant**：功能组合/产品形态，如配套 HMI、通信、附加功能。
- **Board**：硬件板型、MCU、引脚、时钟和板级差异。
- **Release**：固件/App 等的软件发布基线与验证记录。

三者相互独立管理；具体文件组织、配置生成、版本兼容矩阵在架构阶段确定，不在 P0 直接指定实现。

## 5. P0-05｜总体研发策略与管理方法

### 5.1 方法与阶段原则

采用**需求和证据驱动、总体设计与分步验证结合**的工程方式。参考系统工程/V 模型、Automotive SPICE 的过程思想及汽车电子质量实践，按单人开发+AI 协作现实裁剪。过程包括：项目目的与现状认识 → 使用场景/系统需求 → 系统架构与接口 → 软硬件详细设计 → 实现和模块测试 → 集成与系统验证 → 发布及维护；不是要求所有事情串行停滞，不取消必要的前置审查。

**当前明确只推进 P0**。进入后续范围前应记录 P0 决定与未决条件，不能因为现有代码存在就把既有软件认定为已通过需求、架构或验证。允许早期的隔离研究继续作为历史资产/实验记录，但其成果必须在后续阶段按有效需求重新核对。

### 5.2 专业架构和技术策略（只固定原则）

- 核心制动业务尽量跨 MCU/板型复用；软件采用可审查的轻量 ASW/BSW 分层，不预设复杂框架。
- MCU 基础驱动复用已核验的官方 SDK；板级能力、引脚和时钟必须有来源。
- MCU 代码使用 C；命名清晰稳定，中文注释针对职责、契约、硬件依据、异常与安全约束；main 保持简洁。
- App、LCD 不承担主控实时闭环决策；跨方向接口由共同的、版本化的协议定义约束。
- 版本管理使 Variant、Board、Release 不混淆，不因个别迭代覆盖历史可用基线。

上述属于已知工作原则，不构成对具体 ASW 模块接口、任务调度周期、CAN DBC、BLE GATT/AT 结构、控制算法或目标芯片选型的批准。

### 5.3 研发增量及验证原则

分阶段形成证据：

`资料/方案核对 → 源码与静态检查 → Host 单元/模块测试 → 目标芯片编译 → 下载烧录 → 开发板功能实测 → 多模块/系统集成 → 故障注入与执行链验证 → 产品级确认`。

此链不暗示所有活动必须完全串行；它强调**证据等级不可跳级命名**。实际制动输出需要单独设计与授权；在产品安全状态和故障关断路径未验证前不允许开放真实执行功率。

### 5.4 工作成果和配置管理

- 项目目标、需求、设计、代码、测试、风险与决定之间建立版本关系，重要变化应定位实际受影响项。
- 研发源码以对应专业分支的准确 HEAD/发布标签作为代码证据；管理系统不反向篡改工程历史。
- 每个正式实施任务应有明确输入版本、文件范围、禁止动作、期望输出、测试条件与结果回执。
- 原始构建日志、测试日志、设备测量与缺陷复现由实际执行人产生，AI 不补造 PASS。
- 关键技术论证、控制策略、故障保护及产品配置变化必须有可读决策记录，方便负责人长期学习和维护。

### 5.5 P0 之后最近的工作方向（仅列准备，不授权执行）

P0 完成后，先进行**现状/可行性证据复核与系统需求研究**：包括传感/制动信号来源、控制需求、功率执行和安全策略、BLE/APP 交互约束、目标市场法规适用性、初期产品 Variant 选择。其细化任务、优先级及是否可以并行，由下一阶段审查决定；本稿不提前冻结它们。

#### 2.2.1 图纸与旧手册的实际差异（直接影响驱动配置）

- **MCU/版本标注：** RevC 原理图第 1 页 U4 标为 `YTM32B1LE05H0VLHT`，旁注“RevC: MCU 为 YT-PCN-2511B 后新芯片”。参考手册是 RevA 且只给出产品系列名。因此必须先核实实际 PCB 丝印/MCU 顶标/SDK 芯片修订适配，不可把旧 bring-up 工程的 SDK 版本当作已适配新芯片。
- **I²C 通道冲突：** RevA 参考手册第 5 页（正文第 3 页）的 EEPROM 表，将 **PTD1/PTD0** 标为 `I2C0_SCL / I2C0_SDA`；RevC 原理图第 1 页把相同引脚的 MCU 复用功能标为 **`I2C1_SCL / I2C1_SDA`**，第 3 页的 EEPROM U6/J8 也连接到 `EEP_I2C_SCL/EEP_I2C_SDA`。这些是两个文件中的**不同定义**，尚不能凭纸面确认实际评估板 GPIO PinMux 应配置 I2C0 还是 I2C1，需依实物芯片修订及对应 SDK 的 pinmux 定义核定。
- **可见基础电路：** 原理图第 3 页能看到 CAN 收发器 U5、USB 转串口 U8、I²C EEPROM U6、LIN 等板载电路；第 1 页看到 CAN 信号、UART1 等 MCU 引脚，手册列出 J1/J2 供电跳线和直接引出排针。这里的 **PWM/电机控制扩展接口不等于房车制动器功率驱动板**。评估板未因此获得制动器供电、电流检测、功率级故障关断能力。
- **供电与逻辑电平：** 参考手册列出 J1 12V/USB 5V 供电选择与 J2 MCU VDD 5V/3.3V 选择。外接蓝牙与加速度模块是否可直接接线，必须以模块板级供电范围、引脚耐压、信号电平以及当前 J1/J2 实际跳接为准；不能只依据芯片名假设可以直连。
- **其他 RevC 变更：** RevC 页 4 说明电位器供电、AN0/RP0 丝印变化；页 1 有 SPI/编码器相关标注。涉及到使用上述功能时应以实际板版本为依据，不以 RevA 手册替代核对。

## 4. 产品与技术路线的历史差异

### 4.1 制动状态与减速度来源

**来源 A（历史 V1.1）**：采用刹车信号识别制动状态，使用加速度计获取纵向减速度；该版写明“当前方案不依赖牵引车 CAN 总线”。

**来源 B（近期用户研发方向）**：希望优先开展 CAN、加速度传感器与蓝牙等基础能力。固件仓库同时具备 CAN 抽象接口与 BMA510 I2C 驱动。

**当前评价：`UNRESOLVED_SCOPE_EVOLUTION`。** 不能仅据 CAN Driver 源码存在，就推断产品未来必须依赖牵引车 CAN；也不能因为旧文档写了“不依赖”就否决新 CAN 验证研究。至少需要在后续需求中回答：CAN 是辅助车辆信息、外部 CAN 加速度传感器通信、制动状态主来源，还是作为扩展接口？各信息源故障时谁有效，何时参与控制？

### 4.2 重量档与制动力等级

历史方案 V1.0/V1.1 描述的六档、1.0–4.0 t 是**示例**，并要求由目标车型范围及实车标定决定；App 当前 UI/Mock 固定重量档为 1/2/3，并使用 1–10 制动力显示。**三档 Mock 与六档历史示例不一致，并不等于代码存在产品缺陷**，因为首款档位数还未批准。后续需求应先冻结配置语义和有效范围，再审查 UI 与固件接口。

### 4.3 App/LCD、手动制动与后续扩展

历史文档给出了普通 LCD 与智能 App 方案；具体首款组合、Android/iOS 覆盖、手动制动、OTA、侧摆辅助等仍应由产品需求/Variant 决定。现有 Flutter 界面不能倒推出产品发布范围。

### 4.4 软件先行与安全工程顺序

可继续并行整理 SDK、接口及 Host 测试，不代表可以绕过制动功率执行的安全研究。尤其不能简单规定“所有故障一律断开制动力”为通用安全答案，安全状态需按工况、危害和硬件能力论证；当前仅保持软件执行输出禁止状态。

| `SC-08` | 外设验证：工程师在云途开发板连接蓝牙/加速度模块，验证接口与数据，不牵连真实执行功率 | 接线错误、电平不适配、传感数据无效、CAN Bus-off | `SYS-LAB`, `SYS-IN`, `SYS-COM` |
| `SC-09` | 产品配置切换：不同 MCU/Board/Variant 复用控制语义，测试证据不会跨板误认 | 引脚冲突、驱动差异、配置混装、发布版本不一致 | `SYS-PLAT`, `SYS-DIAG` |
| `SC-10` | 真实产品集成：未来接入电磁制动器与功率驱动前必须满足单独的系统/硬件安全准入 | 上电、掉电、看门狗、驱动失控、供电波动、错误制动输出 | `SYS-OUT`, `SYS-SAFE`, `SYS-QUAL` |

**场景边界**：使用案例是用户任务及期望结果，不是 UI 页面/驱动名称。比如 `SC-03` 不预先要求加速度由 I²C BMA510 获得，也不宣称 CAN 必须来自牵引车。

## 3. 系统与外部环境边界

### 3.1 逻辑边界

```text
[牵引车制动相关输入]     [运动/减速度相关输入]
            \                 /
             \               /
              [BrakeSync 主控制器]
              | 信号与状态评估 |
              | 制动策略与请求 |
              | 参数、故障诊断 |
                /           \
       [HMI/App]       [功率执行与制动器]
     设置/查看/维护        （未来独立安全准入）
```

- `BrakeSync 主控制器` 是自动制动控制职责主体；**手机、LCD 和云端不参与必须实时闭环**。
- `外部输入` 至少包含制动意图/触发信息和运动相关信息的**逻辑概念**；哪些是主输入、冗余、辅助或可选须经 `OD-02` 决定。
- `功率执行` 属产品长期范围，但现有 EVB 没有受控的实际制动功率执行方案；不得将目标输出 API 已存在视为硬件准入。
- `接口技术`（CAN、I²C、UART、BLE）及 `软件分层` 是后续设计/实现约束，并非所有产品 Variant 的无条件系统需求。

### 3.2 初始产品配置管理逻辑

- **共用核心**：输入质量、系统状态、配置语义、制动请求边界、故障与验证语义尽量相同。
- **Variant**：决定是否有 LCD/App、可选功能、用户交互/诊断能力；不暗中改变共用语义。
- **Board**：决定目标 MCU、引脚/电源/通信外设、硬件关断路径；当前 `YTM32B1LE0-EVB-LQFP64` 是**验证板**，不是量产 MCU 冻结决定。
- **Release**：标识系统软件/协议/配置及适用板型的发布；不得将固件和 App 任意组合宣称兼容。

### 5.2 安全、网络和合规的处理原则

- **功能安全**：P2 识别危险源与需求主题，后续必须建立适合目标车辆场景的危害分析和执行安全要求分配。本文**不是 HARA、ASIL 判定或安全案例**。
- **安全状态不能空泛**：例如“传感器故障直接切断制动力”是否安全须考察正在制动/未制动、道路工况、执行器模式与其它可用信息，不能全局拍板。
- **网络/配置安全**：与制动相关的写操作在身份、完整性、授权、回执、超时和冲突机制未确认前，不连接真实执行链；App UI 演示可使用 Mock。
- **法规与认证**：目标市场/车辆类别尚未确定，不能宣称已符合特定标准；产品阶段必须确认适用法规、试验和责任分工。
- **当前研发禁令**：开发板阶段只做无功率输出的功能验证，不允许借 P2 的任何候选要求释放真实制动功率。

### 6.1 当前存在的具体硬件资料冲突

## 2. 系统上下文及接口边界

```text
牵引车/驾驶员操作、外部传感器、用户配置
        │          │            │
        └───────[ 受控的输入/通信边界 ]─────────────┐
                                                   ▼
                                      ┌─────────────────────┐
                                      │ BrakeSync 核心控制器 │
                                      │ 输入质量 / 状态 /    │
                                      │ 参数 / 控制 / 诊断   │
                                      └─────────────────────┘
                                          │            │
                                  [输出请求合同]   [状态/配置合同]
                                          │            ├── LCD（若配置）
                                          │            └── BLE ↔ App（若配置）
                                          ▼
```

- **主控制器**负责制动相关决策、状态、信号质量、配置有效性与故障处理；不得以 App 在线为先决条件。
- **App/LCD** 负责呈现、提交受许可的设置请求、读取结果；不得直接写功率 PWM 或绕开主控状态判断。
- **执行器边界** 把业务制动请求与电流调节、PWM、驱动器、物理制动器分离；实际执行硬件属于未来独立安全论证事项。某些故障的正确安全反应取决于危险分析，不应武断写“所有情况下直接切断即安全”。
- **外部接口** 不假定牵引车 CAN 必需；如果加速度模块以 CAN 输出，仅说明传感器通信，不能据此更改产品的牵引车 CAN 依赖。

## 6. 状态与安全责任边界

系统级候选状态：`INIT`（启动/检查）、`INHIBITED`（未满足启用条件）、`READY`（输入、配置及安全许可可运行）、`ACTIVE`（有效制动请求处理中）、`DEGRADED`（受限运行，条件待危害分析）、`FAULT`（需明确故障处理）、`MAINTENANCE`（受控服务模式）。

这些是语义候选，**不是已经评审完的安全状态机**。特别要核对：初始化失败、参数损坏、传感器无数据、通信错乱、复位、低压、看门狗、执行器异常和异常恢复；不同故障与车辆工况可能要求不同动作。`READY` 更不能仅靠软件标志判断功率硬件具有安全准入资格。

**当前 EVB 强制硬边界**：`BrakeSystem_CanEnableBrakeOutput()` 在读取到的固件快照中返回 `false`，但该源码事实不能证明电气接口天然安全。实物接线与后续代码须继续保持无执行功率路径，任何意外输出都应视为阻塞问题。

## 7. 与现有云途板的接口核对

- 用户已确认 `YTM32B1LE0-EVB-LQFP64`；RevC 原理图为 5 页，RevA 评估手册 16 页，两份文件**并非同一已证实 PCB 修订**。

## 5. 蓝牙 App 共同接口定义（ICD 候选骨架）

后续形成一份权威 `BLE-ICD`，不允许固件与 App 分别猜测。至少包含：

- 传输事实：外接模块确切型号/固件、UART 电平和参数、是否 AT/透明传输、BLE 服务及特征 UUID 的原厂或现场证据；
- 设备身份：产品设备 ID、配对方式、许可角色、鉴权、会话超时、重放保护；
- 请求与回执：协议版本、消息类型、事务/请求 ID、长度、数据类型、校验、错误码、设备端执行状态；
- 设置与回读：`weightPreset` 和 `brakeLevel` 的单位、有效范围、提交/生效/持久化时机，断连前后的一致性；
- 状态和故障：设备运行/连接/受限/故障的代码表、时间戳与缓存标志；
- 兼容与回滚：App 与固件的协议版本组合、未知字段策略、不可恢复错误提示；
- 测试：伪设备、越界命令、重放、断连、重连、超时、写失败、掉电重启、升级前后兼容。

**严禁使用当前 Flutter Mock 的三档示例当最终重量档数量，严禁将历史 WLT8016 规格引用当作已经得知 GATT UUID。** 真正危险的执行动作不得通过普通 App 配置写入路径绕开安全准入。

## 6. CAN 与加速度设备适配详细合同

1. 首先确认手中模块究竟是 CAN 加速度模块还是直接 I²C/SPI BMA510 板；若是前者，需要整套**模块级**报文协议、供电和 CAN PHY/终端说明；若是后者，需要模块板级电平/引脚和原厂芯片配置与实测。
2. 目标 CAN 接收必须区分总线中断处理与业务消息处理；过滤、FIFO/队列、丢包、Bus-off 恢复的策略不可由 `main()` 临时堆砌。具体中断/DMA 实现由精确 YTMicro SDK 决定。
3. I²C 开发板 EEPROM PTD0/PTD1 的 RevA vs RevC `I²C0/I²C1` 差异属于工程阻塞项；不能把手册旧编号当可靠复用；按实际芯片 SDK 与原理图先核对。
4. 预留设备健康、采样新鲜度、单位、零偏、温度/自检及故障码；正常数据与坏数据用一致上层合同表示。

## 7. 参数、诊断和安全设计

- **参数**：独立决定用户档位/等级与受保护的工程标定区；有效值与正在编辑值分开；掉电原子性、默认和版本迁移需测试；保存操作的生命周期可追踪。
- **诊断**：故障事件表至少列检测原因、检测条件、错误计数/去抖、严重度、锁存/恢复、对 HMI 的可见语义及对应测试。不得用“返回 false”代替全部故障理由。
- **安全**：先形成危险清单、运行工况和允许动作矩阵，确认软件/硬件安全分配；目前 `BrakeSystem_CanEnableBrakeOutput() == false` 只能作为读取到的旧源码事实，不是硬件证明。
- **执行器**：后续真实电磁制动执行需电气/热/过流/短路/断线、复位和故障安全实现数据，不能因为 P4 有章节便开始焊接功率输出。

每条用例至少写明：**需求 ID、测试版本、进入状态、设备配置、输入/操作步骤、预期可观测结果、采样与计量方法、故障注入方法、完成准则、数据文件、缺陷/复验链接**。如果某个阈值（超时、最大延迟、PWM/电流、控制精度）还没有确定来源，填写 `TBD` 并列为阻塞，不靠工程师随手选择一个“看起来合理”的数字。

## 4. 失效与安全验证重点

### 4.1 当前 EVB 阶段

- 端口未绑定或模块缺失时，系统不能将空数据判成“传感器有效”；
- 输入源丢失、停更、校验失败或时钟异常时不产生未经批准的逻辑有效请求；
- 状态机上电/复位/错误/恢复路径可被独立测试，而不是只覆盖正常主循环；
- 蓝牙断连不会中断主控的独立控制职责，也不允许手机因断连/重放错误设置；
- 参数断电/写失败后的预期生效值和故障状态明确；
- 固件/接线/调试指令不具备实际制动功率使能能力；这条需要软件与硬件独立审查。

### 4.2 未来真实产品阶段（本次禁止宣称已覆盖）

真实产品必须在确定电磁制动器类型/数量、载荷、车速、附着、温度、供电、执行器驱动拓扑之后，识别危险和相应故障响应。故障可能需要受控降级而非简单关断；必须基于具体工况、法规定义和风险分析决定。应覆盖上电瞬态、掉电/欠压、MCU 死机、看门狗、驱动短路/开路/粘连、器件热失控、传感器异常、用户误设置、线路接触不良等，保留可重复的试验结果。

ISO 26262、Automotive SPICE、MISRA C 仅作为当前适用性研究与过程借鉴，不可宣称认证通过或任何 ASIL 等级。是否适用特定产品须按目标区域和用途调查。

## 5. 验证覆盖与度量规则

- **需求覆盖** = 有确定验证计划的批准需求 / 适用的已批准需求（计划覆盖）；
- **已执行覆盖** = 至少完成一次适用测试的需求 / 适用的已批准需求；
- **通过覆盖** = 证据显示全部必须判据通过的适用需求 / 适用的已批准需求。
