## 0. 面向负责人的结论摘要

**结论 P1-J01：项目具备继续开展系统需求研究和专项验证的基础，但不存在可据以宣称“完整控制器可工作、可装车或可量产”的证据。**

- **可继承资产已经形成**：固件 ASW/BSW 分层骨架、若干 Driver/CDD 源码、BMA510 设备访问逻辑、WLT8016 UART 字节层、部分云途 GPIO 适配、Host 单元测试；Flutter App 的模拟界面、抽象数据层和测试；历史产品方案与管理工具均已存在。
- **有新确认的自动化证据**：当前固件精确 HEAD 的 GitHub Actions `firmware-host` 成功，步骤包含 Configure、Build、Test；当前 App 精确 HEAD 的 `app-static` 成功，步骤包含 Dependencies、Analyze、Test。这是 **CI 中特定检查通过**，不是目标芯片构建、实物运行或产品验收。
- **当前最大的工程缺口**：已确认评估板与 RevC/RevA 文件的**实物版本匹配**、对应新芯片 SDK/PinMux/时钟/中断/总线适配、蓝牙与加速度模块的板卡规格和接线、制动触发和减速度信号来源、实际功率执行和故障安全通路、BLE 模块可用软件协议、App—固件一致接口以及对应实物验证证据。
- **历史方案与最新研发方向尚需对齐**：产品 V1.1 明示当前方案不依赖牵引车 CAN；近期开发对话希望优先开展 CAN 和加速度传感器工作；BMA510 原厂资料证明的是传感器芯片接口，并不能证明用户手中的模块是 I²C BMA510，或将其等同 CAN 加速度模块。这可能是新增扩展、替换输入来源或实验验证，现有证据不足以宣布产品需求已变更。历史材料同时包含六档示例重量区间，App Mock 只有三档按钮；两者均不能被直接当作冻结的产品档位数。
- **建议的 P1 退出结论**：**“允许进入有边界的后续系统需求与关键可行性研究”可作为候审建议**，不等同硬件技术可行性已证明，更不授权释放制动输出。

### 1.3 证据等级及判定方式

- **E0 — 来源存在**：文件、历史文本或源码可定位，不代表内容正确。
- **E1 — 源码/合同检查**：已阅读接口和代码行为，尚未执行其运行验证。
- **E2 — 自动化 Host/静态验证**：可核对**对应 HEAD** 的 CI 检查/步骤结果；仍只适用于所运行环境与范围。
- **E3 — Target 构建与下载**：有准确 MCU、SDK、编译器及原始日志等证据；烧录单独记录。
- **E4 — 实板/模块验证**：有设备接线、配置、测量与失败记录，能重复执行。
- **E5 — 系统、故障与产品级验证**：需求和安全目标有相应系统证据、适用产品配置及正式审阅记录。

当前 **E2 不能被表述成 E3～E5**。其中“未见证据”只表示本轮访问范围未取得，不能推断用户在其他地方从未做过测试。

#### 2.2.1 图纸与旧手册的实际差异（直接影响驱动配置）

- **MCU/版本标注：** RevC 原理图第 1 页 U4 标为 `YTM32B1LE05H0VLHT`，旁注“RevC: MCU 为 YT-PCN-2511B 后新芯片”。参考手册是 RevA 且只给出产品系列名。因此必须先核实实际 PCB 丝印/MCU 顶标/SDK 芯片修订适配，不可把旧 bring-up 工程的 SDK 版本当作已适配新芯片。
- **I²C 通道冲突：** RevA 参考手册第 5 页（正文第 3 页）的 EEPROM 表，将 **PTD1/PTD0** 标为 `I2C0_SCL / I2C0_SDA`；RevC 原理图第 1 页把相同引脚的 MCU 复用功能标为 **`I2C1_SCL / I2C1_SDA`**，第 3 页的 EEPROM U6/J8 也连接到 `EEP_I2C_SCL/EEP_I2C_SDA`。这些是两个文件中的**不同定义**，尚不能凭纸面确认实际评估板 GPIO PinMux 应配置 I2C0 还是 I2C1，需依实物芯片修订及对应 SDK 的 pinmux 定义核定。
- **可见基础电路：** 原理图第 3 页能看到 CAN 收发器 U5、USB 转串口 U8、I²C EEPROM U6、LIN 等板载电路；第 1 页看到 CAN 信号、UART1 等 MCU 引脚，手册列出 J1/J2 供电跳线和直接引出排针。这里的 **PWM/电机控制扩展接口不等于房车制动器功率驱动板**。评估板未因此获得制动器供电、电流检测、功率级故障关断能力。
- **供电与逻辑电平：** 参考手册列出 J1 12V/USB 5V 供电选择与 J2 MCU VDD 5V/3.3V 选择。外接蓝牙与加速度模块是否可直接接线，必须以模块板级供电范围、引脚耐压、信号电平以及当前 J1/J2 实际跳接为准；不能只依据芯片名假设可以直连。
- **其他 RevC 变更：** RevC 页 4 说明电位器供电、AN0/RP0 丝印变化；页 1 有 SPI/编码器相关标注。涉及到使用上述功能时应以实际板版本为依据，不以 RevA 手册替代核对。

#### 2.2.2 现阶段软件工作与实测边界

1. **可以先建、可独立 Host 测试：** ASW/BSW 职责、板型配置、系统状态、信号质量、参数合同、制动策略数学模型与无输出的诊断/异常场景；不要求最终 PCB 已有。
2. **可以在评估板上有条件实测：** UART、CAN、I²C、DMA/IRQ、计时、蓝牙字节链、加速度数据链。前置条件是实物版本/引脚、模块电气与 SDK 证据匹配，记录命令、接线、版本、数据和故障路径。
3. **禁止以当前评估板验证替代：** 最终制动功率驱动、硬件默认禁能与故障关断、电磁制动器负载、整车动态、产品供电和法规/量产性能。
4. **模块身份必须分离：** `Bma510.c` 当前是假 I²C 主机单元测试实现，并不能证明真实加速度模块是 BMA510；历史曾出现“CAN 加速度传感器”描述。确认模块实物后再判定它属于芯片级 I²C/SPI 驱动还是带协议的 CAN 设备。`Wlt8016.c` 同理不能证明蓝牙实物一定是 WLT8016 固件版本。

## 4. 产品与技术路线的历史差异

### 4.1 制动状态与减速度来源

**来源 A（历史 V1.1）**：采用刹车信号识别制动状态，使用加速度计获取纵向减速度；该版写明“当前方案不依赖牵引车 CAN 总线”。

**来源 B（近期用户研发方向）**：希望优先开展 CAN、加速度传感器与蓝牙等基础能力。固件仓库同时具备 CAN 抽象接口与 BMA510 I2C 驱动。

**当前评价：`UNRESOLVED_SCOPE_EVOLUTION`。** 不能仅据 CAN Driver 源码存在，就推断产品未来必须依赖牵引车 CAN；也不能因为旧文档写了“不依赖”就否决新 CAN 验证研究。至少需要在后续需求中回答：CAN 是辅助车辆信息、外部 CAN 加速度传感器通信、制动状态主来源，还是作为扩展接口？各信息源故障时谁有效，何时参与控制？

### 4.2 重量档与制动力等级

历史方案 V1.0/V1.1 描述的六档、1.0–4.0 t 是**示例**，并要求由目标车型范围及实车标定决定；App 当前 UI/Mock 固定重量档为 1/2/3，并使用 1–10 制动力显示。**三档 Mock 与六档历史示例不一致，并不等于代码存在产品缺陷**，因为首款档位数还未批准。后续需求应先冻结配置语义和有效范围，再审查 UI 与固件接口。

### 4.3 App/LCD、手动制动与后续扩展

历史文档给出了普通 LCD 与智能 App 方案；具体首款组合、Android/iOS 覆盖、手动制动、OTA、侧摆辅助等仍应由产品需求/Variant 决定。现有 Flutter 界面不能倒推出产品发布范围。

### 4.4 软件先行与安全工程顺序

可继续并行整理 SDK、接口及 Host 测试，不代表可以绕过制动功率执行的安全研究。尤其不能简单规定“所有故障一律断开制动力”为通用安全答案，安全状态需按工况、危害和硬件能力论证；当前仅保持软件执行输出禁止状态。
