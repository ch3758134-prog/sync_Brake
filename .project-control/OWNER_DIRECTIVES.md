# BrakeSync｜负责人工作约束（历史用户表达索引，V0.1）

> 这是对可访问项目对话记录、项目长期规则和本轮明确指令的提炼，不是逐字的全量聊天纪要，也不是正式需求/Gate/ASIL 批准。遇到准确表述或后续修订冲突，应回到原始对话及最近用户指令核对。记录日期：2026-11-12。

## 产品与开发目标

1. **面向真实产品而非 Demo**：构建面向拖挂式房车的电子同步制动控制技术体系，综合可靠性、可维护性、实际安全、成本竞争力与产品迭代。
2. **共享平台、可配置产品**：共用核心制动控制软件，允许 LCD、按键、蓝牙和车辆信息等不同 Variant；`Variant`（功能形态）、`Board`（MCU/硬件板型）、`Release`（软件发布）分别管理。
3. **控制独立于手机**：用户使用手机 App 或 LCD 主要进行参数设置和状态查看；独立控制器承担自动制动。产品 V1.0/V2.5 历史文档支持此方向，但具体参数待有效工程需求确认。
4. **产品交互重点**：房车重量制动档与制动力等级是两个概念；App 初期关注 BLE 设备搜索/连接、设备与故障状态、重量档与 1–10 级制动力操作。LCD、车机、扩展功能的实施范围不得从历史示例自动推导。

## 技术架构与安全

5. **参考汽车电子过程，但合理裁剪**：采用轻量 ASW/BSW 分层，应用控制算法避免直接引用 MCU SDK/寄存器；底层复用官方 SDK；清晰区分 Driver、Service、BoardCfg 等边界，避免过度包装。
6. **硬件依据优先**：具体 MCU/EVB、时钟、引脚、DMA/IRQ/CAN/I2C/UART、芯片版本及功率执行电路以真实 SDK、原理图、源码与测试为准。开发板仅为评估与驱动验证，非最终产品选型。
7. **制动安全优先**：必须定义上电安全态、输出禁止、硬件故障关断、故障恢复和验证依据；未完成确认时不能因软件接口存在而允许实际制动输出。
8. **验证分层**：明确区分源码已写、Host Build、Target Build、烧录、运行、实板功能、故障注入和产品级验证；不把部分通过包装成产品可用。
9. **代码风格**：MCU C 语言，职责、接口、状态、异常处理明确；稳定英文命名、简洁中文注释，尽量减少全局隐式依赖；可读性方便负责人理解、学习、审查与持续维护。

## 工作组织与权限

10. **负责人掌握软件**：负责人负责技术方向决策和验收，也需要理解代码细节；AI 可研究、设计与形成明确实施方案，Codex 负责按界限修改、编译与测试，不由执行 AI 决定架构。
11. **平行专业研发**：固件研发与手机 App 研发各有独立对话/执行范围；App 不擅自改固件架构，共享通信协议由两专业共同审查。CAN、加速度计和蓝牙相关基础开发受到近期关注。
12. **管理分支约束（本轮直接指令）**：工程协调 AI 只写 GitHub `management` 分支，可只读其他分支；不修改 `main`、`firmware` 或 `app`，也不擅自合并。
13. **管理基线授权（本轮直接指令）**：负责人明确要求按项目对话优先恢复用户目标，建立管理基线。本次授权适用于初始化管理性文件，不等于批准产品计划、需求、硬件动作、发布或 Codex 任务。

## 后续要追踪而不是凭空填数的事项

- 最终目标 MCU/硬件板、具体 SDK 版本与全部外设资源；功率执行电路、制动器/轴数、额定电源及安全关断路径。
- 房车覆盖重量、档位数与重量区间、制动力映射/标定、响应/失效策略；V1.0 的重量分档仅为示例。
- BLE 芯片/固件版本、UART 模式、AT、GATT UUID、命令协议、身份鉴权、确认与超时；目前不得默认 WLT8016 能直接被 App 按猜测协议安全操作。
- 是否实施手动制动、OTA、车机扩展等可选能力：保留候选，待独立明确。
